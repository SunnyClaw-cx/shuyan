# ERP 企业套件

一个用枢言（`.sy`）写的**六模块企业级工程**，用于验证「中文原生语言能不能
扛住**互相依赖的套件**」。它按真实 ERP 口径实现了采购、库存、销售、财务四条
业务线，并保证了三条企业级约束：**复式记账恒等式**、**成本与总账相符**、
**事务部分失败不留半截状态**。

## 为什么做这个工程

前面的 `应收对账` 已经证明「单点业务能写」。但它回答不了新的问题：

1. **多模块互相依赖**能理清吗？六层依赖会不会绕一圈又回来？
2. **状态**放在哪？服务层若随手改入参会怎样？
3. **没有回滚**的语言，怎么保证「一张收货单同时改订单 / 库存 / 应付」不出半成品？

本工程用**真实企业需求**来回答。结论写在最后。

## 运行

```bash
sy 运行 projects/ERP/主程序.sy
```

## 文件结构

| 文件 | 职责 | 依赖 |
|---|---|---|
| `主数据.sy` | 类型中枢：5 枚举、3 结构体、编号与金额工具 | 无（仅 `文本`、`数学`） |
| `库存服务.sy` | 移动加权平均、出入库、盘点调整 | `主数据`、`数学` |
| `采购服务.sy` | 采购订单、收货推进、应付口径 | `主数据` |
| `销售服务.sy` | 销售订单、发货推进、信用检查、毛利 | `主数据` |
| `财务服务.sy` | 复式记账三铁律、红冲、余额与试算 | `主数据` |
| `企业.sy` | **状态持有** + **事务编排**（两阶段提交） | 以上五个 |
| `主程序.sy` | 编排演示：走完整业务链并自证 | 全部 |

依赖是**单向**的：`主程序 → 企业 → 五个服务 → 主数据`。
没有循环引入，底层不知道上层存在。

## 架构决策（两条，都值得说明）

### 一、服务层无状态，状态集中一处

`库存服务` / `采购服务` / `销售服务` / `财务服务` 全是**纯函数**：
只接收数据、返回新数据，**绝不改入参**。真正的状态（物料、单位、科目、
库存台账、订单表、账簿、各单据序号）全部集中在 `企业.sy`。

原因：枢言的 `定义 乙 = 甲` 是**引用**，列表切片与映射合并也只是**浅拷贝**。
服务层若随手改入参，调用方持有的对象会被悄悄改掉 —— 跨模块排查极难定位。
分层后，**改状态只有一处**，可追踪。

状态更新一律**整体替换**（`库存台账 = 新台账`），而不是就地改字段。
新对象进、旧对象出，语义干净。

### 二、两阶段提交（因为语言没有回滚）

一张收货单要**同时**改三处：订单某行 `实收数量 +N`、库存台账、账簿记凭证。
三处必须同生共死，但枢言没有事务回滚 —— 第③步失败，前两步不回退，账就烂了。

应对办法是**两阶段提交**：

| 阶段 | 做什么 | 硬约束 |
|---|---|---|
| **预演** | 把三处要做的改动**先算出来**（只调纯函数） | **一个字节都不改**（连凭证号都不发，用空号占位校验借贷平衡） |
| **提交** | 预演全过，才把结果写回状态变量 | 只做赋值与入账，不会再失败 |

「预演绝不改状态」是命根子 —— 因此**编号分配全部推迟到提交阶段**。
若在预演就发号，一次失败的收货会白白吃掉一个凭证号，既污染账，
也让「预演无副作用」站不住。

这就是「先把所有可能出错的事做完，再做不可能出错的事」。

## 业务规则（都有明确口径）

| 规则 | 口径 |
|---|---|
| 金额 | **一律整数分**，全程不做浮点运算 |
| 记账 | 有借必有贷、借贷必相等、凭证不可改只能红冲 |
| 成本 | 移动加权平均；出库**先乘后除再取整**，减少截断尾差 |
| 盘点 | 盘盈盘亏走「待处理财产损溢」，不直接冲减成本（会计准则要求） |
| 信用 | 本次发货收入 + 已占用 > 额度 ⇒ 拦截发货 |
| 单据状态 | 草稿 → 已审核 → **已执行** → 已完成（另含已作废） |
| 分录 | 每张凭证写**显式两条分录**，不用负数分录破坏「借贷合计」的语义 |

## 演示流程

`主程序.sy` 依次走六段：

1. **主数据登记** —— 3 物料 / 2 单位 / 7 科目
2. **采购入库** —— 一单三行逐行收货，含一次**已收齐拦截**
3. **库存台账** —— 移动加权平均单位成本、低库存预警
4. **销售发货** —— 成本结转 + 毛利，含**库存不足**与**信用超额**两次拦截
5. **盘点调整** —— 盘亏一次，账实相符一次
6. **期末结账** —— 试算平衡、科目余额、**存货核对**、本期毛利

## 这个工程验证了什么

### 结论：业务层够用，缺的是基础设施

- **多模块套件可写**：六层单向依赖，类型跨模块传递正常。
- **企业约束可表达**：复式记账、状态机、事务编排、成本核算 ——
  **全部用现有语法写出，没有为它新增任何语言特性**。
- **缺的是基础设施**：没有网络 / HTTP 模块，也没有事务引擎 ——
  后者用「两阶段提交」在**应用层**补上，代价是编排代码变长。

### 自证式输出（跑一遍就能核对）

工程末尾会自己核对两件事，不需要人肉验算：

```
  存货核对：库存台账 9,577.50  总账「库存商品」 9,577.50  真
  试算平衡：真  借 20,677.50  贷 20,677.50
```

- **存货核对**：库存台账金额必须 = 总账「库存商品」科目余额。
  两套账对不上，说明成本结转或记账漏了 —— 这是 ERP 最容易出的错。
- **试算平衡**：全账借方合计必须 = 贷方合计。只要每张凭证都平，
  试算必然平衡；不平衡就说明账簿被绕过唯一入口篡改了。

### 本工程修掉的一个业务缺陷：状态机少一态

初版单据状态机只有 `草稿 / 已审核 / 已完成`，缺 `已执行`。
后果：一个订单**部分收货后若恰好收齐**，状态直接跳「已完成」；
而**未收齐但已收一部分**的订单状态仍是「已审核」——
与「一行未动」的订单**无法区分**。

更糟的是报错文案：继续收货时报「订单未审核，不能收货」，
而真因是「已收齐」—— **报错点与真因点不一致**，人会查错方向。

修法：启用枚举里**早已定义却从未使用**的 `已执行`；
收货/发货时状态置 `已执行`，收齐才置 `已完成`；
失败文案按**实际状态**分三种（未审核 / 已收齐 / 已作废），不再一律说「未审核」。

这与项目里反复出现的一条教训同源：**报错点 ≠ 真因点时，必须在真因处说清**。

## 可复现性

本工程随 `sy 检查 examples/*.sy projects/*/*.sy` 一起被自动检查，
`sy 检查` 必须对它**零错误、零警告**；`主程序.sy` 必须**完整跑通退出码 0**。
这是「对外声明的数字必须有脚本能跑出来」这一约定的具体落实。
