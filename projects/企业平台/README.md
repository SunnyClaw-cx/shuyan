# 企业中台

一个用枢言（`.sy`）写的**十四域企业级中台工程**，规模 **78 个文件 / 6.2 万余行**，
用于验证「中文原生语言能不能扛住一个**真正的企业级系统**」——
不是示例、不是玩具，而是有框架层、有分层、有跨域编排、能完整跑通并自证的中台。

它回答的是 `ERP` 工程回答不了的规模问题：**当域从 1 个变成 14 个、
文件从 7 个变成 78 个、行数从几千变成六万，语言还站得住吗？**

## 运行

```bash
sy 检查 projects/企业平台/主程序.sy     # 静态检查：零错误、零警告
sy 运行 projects/企业平台/主程序.sy     # 端到端演示，退出码 0
```

`sy 检查 主程序.sy` 会**递归覆盖**它引入的全部模块（含框架层、各域的
模型 / 仓储 / 服务 / 规则 / 报表），一处有错就会连带报出来。

## 目录结构

```
企业平台/
├── 框架/                平台级基础设施（7 模块，被所有域共用）
│   ├── 基础.sy          金额/日期/对齐/校验 —— 全平台唯一来源
│   ├── 事件.sy          事件总线：定义、订阅、派发
│   ├── 工作流.sy        审批流引擎：节点、状态推进、进度
│   ├── 权限.sy          角色-资源-动作矩阵
│   ├── 规则.sy          规则引擎：命中项、严重度、拦截判定
│   ├── 审计.sy          审计留痕：追加、按对象/操作者/动作追溯
│   └── 报表.sy          表格渲染：列定义、对齐、合计
├── 主数据/              基础档案域（物料/往来单位/科目/仓库/组织/人员）
├── 采购/  销售/  库存/   业务主线域
├── 生产/  质量/  设备/   制造域
├── 财务/  人力/  项目/   管理域
├── 研发/  合规/         研发与合规域
├── 支撑/                流程支撑域
├── 报表/                综合报表域
└── 主程序.sy            跨域编排：装载 → 流转 → 自证 → 报表
```

每个业务域固定 **5 层**：`模型` · `仓储` · `服务` · `规则` · `报表`。

## 架构口径（三条，全工程统一）

### 一、分层单向依赖，域之间不横向引入

依赖只有一个方向：

```
主程序 → 全部域 → 框架
        域与域之间 ✗ 不互相引入
```

域内五层也是单向的：`报表 → 服务 → 仓储 → 模型`。
这样**永远不会出现循环引入**——一个域数不清的依赖图，靠纪律管不住，
只能靠结构保证。

### 二、服务层无状态纯函数，状态集中在主程序

所有域的 `服务` 层都是**纯函数**：只读入参、不改入参、只返回值。
业务状态全部由 `主程序.sy` 集中持有。

原因：枢言的 `定义 乙 = 甲` 是**引用语义**。服务层若随手改入参，
调用方持有的对象会被悄悄改掉，六万行里排查这种问题极其困难。
分层后**改状态只有一处**，且更新一律**整体替换**（`表 = 新表`），
不做就地改字段。

> 仓储层的「增 / 改 / 删」同样**返回新列表**，调用后必须整体替换。
> 主程序里每一次更新都写成 `表 = 仓储.改(表, …)`；少了这次赋值，
> 更新会**静默失效**——这是本项目反复强调的引用语义陷阱。

### 三、金额一律整数分，规则与仓储分离

- **金额**：全工程一律**整数分**，不做浮点运算。`框架/基础` 提供
  `分转元` / `千分位` / `税额` 等唯一实现，业务层不自己算钱。
- **规则**：业务判断抽到 `规则` 层，与数据访问（`仓储`）分离。
  规则是一组命中项，可聚合出「有拦截 / 拦截数 / 结论摘要」。

## 各层都在真实执行

78 个文件按职责分工，**没有一层是摆设**：

| 层 | 职责 | 在演示中的角色 |
|---|---|---|
| 框架 | 事件 / 工作流 / 权限 / 规则 / 审计 / 报表 | 主程序逐一走一遍并输出 |
| 模型 | 类型定义 + 构造辅助 | 装载全部 168 个实体的样本数据 |
| 仓储 | 集合存取（增删改查 / 筛选 / 分页 / 导出） | **每域真实走一遍「查→筛→计数→改→删」并自证** |
| 服务 | 无状态纯函数（校验 / 金额 / 账龄 / 分档） | 规则与报表层的计算来源 |
| 规则 | 规则命中与拦截判定 | 规则引擎演示 |
| 报表 | 按显示宽度对齐的表格渲染 | 每域输出一张明细表 |

仓储层由主程序**真实调用**（装载走 `新增`，演示走 `找 / 按状态 / 计数 /
更新 / 删除`），因此它在依赖链上——`sy 检查 主程序.sy` 能覆盖到它。

## 规模与工程纪律

| 指标 | 数值 |
|---|---|
| `.sy` 文件 | 78 |
| 总行数 | 62,134 |
| 业务域 | 14 |
| 每域实体 | 12（共 168 个实体） |
| 框架模块 | 7 |
| 静态检查 | 78 文件**零错误、零警告** |
| 运行 | 退出码 0，自证通过 |

工程末尾自带**三条不变量校验**，跑一遍就知道成不成，不需要人工核对：

```
自证一：各域实体数范围 6 ~ 6
        装载一致：真
自证二：状态统计覆盖 84 条记录
仓储自证：每域删除行数合计 = 14（应为域数）
```

- **自证一**：各域实际装载的实体数必须一致。不一致说明某个域的数据
  没装全 —— 六万行里人眼看不出，只能让程序自己核对。
- **自证二**：状态统计覆盖的记录数必须等于各域记录数之和。
  对不上说明有记录被静默丢弃。
- **仓储自证**：每个域删除一行后，列表必须恰好少一行（合计 = 域数）。
  这条同时验证了「仓储确实在跑」与「整体替换语义正确」。

这是大型工程里唯一靠得住的做法：**人眼核六万行数据必然出错，
所以不变量必须写成程序自己跑。**

## 确定性生成（可复现）

本工程由 `tools/gen_platform.py` 按**固定种子**生成，
**同一命令两次运行逐字节一致**：

```bash
python tools/gen_platform.py projects/企业平台 \
    --domains 14 --entities 12 --rules 20
```

为什么用生成器而不是手写：手写六万行不现实，且无法验证「规模是不是瓶颈」。
生成器保证**结构一致、命名不冲突、依赖自动补全**，让规模问题可以被
反复实验（改 `--domains` / `--entities` 即可放大或缩小）。

生成器的两条硬纪律：

1. **生成的产物必须零警告**。补全引入会把一个域的十二个实体堆成一条超长
   引入行，生成器会在超宽时按显示宽度自动折行（枢言允许同一模块重复按名
   引入，故折行语义安全）。
2. **生成的每一层都必须被引用**。仓储层的导出名一律带域前缀
   （`{域}_新增X` / `{域}_找X` …）—— 实体名会**跨域重名**（如 `财务报表`
   同时在财务域与报表域），不带前缀时 14 个仓储模块无法被同一主程序引入。
   带前缀后，仓储层就能挂进依赖链，不再是无引用的死代码。

## 这个工程验证了什么

### 结论：能写，且逼出了五处语言缺陷 + 两处结构问题

- **规模不是瓶颈**：六万行、78 文件的静态检查与运行都在可接受时间内完成。
- **框架层可抽**：事件总线、工作流、权限、规则、审计、报表——
  全部用现有语法写出，**没有为它新增任何语言特性**。
- **十四域可组织**：「域内五层 + 域间不横向引入」让依赖图始终是单向的。

写这个工程的过程逼出了五处真实语言缺陷——这些不是猜测，是「写出合法代码
却报了错」或「检查说没问题、运行却崩」的实测结果：

| 缺陷 | 症状 | 真因 |
|---|---|---|
| 模块解析回退工作目录 | 换目录运行就找不到模块 | 违反规范「路径基准=主脚本所在目录」 |
| 引入含错模块冒宿主堆栈 | 报 Python 堆栈而非中文诊断 | 引入路径用「一错就抛」的解析入口 |
| 参数类型只写不查 | 标注了类型也不校验（假通过） | 语义层没做实参类型检查 |
| 同一位置两条诊断 | 一条真实错误被报两遍 | 衍生报错未抑制 |
| 具名参数守卫失效 | 关键字成员名绕过参数检查 | 用了归一名而非源码原文 |

每一处都配了**可复现的探针脚本**（`tools/probe_layout.py` /
`probe_import_error.py` / `probe_derived_diag.py`），修复后必须全过。

工程自身还暴露了两处**结构问题**（已在生成器侧修正）：仓储层一度是无人
引用的死代码孤岛，以及默认批量检查的路径未覆盖分层工程。二者都属于
「声明与实际不符」——一处说「每域五层」却有一层不跑，一处说「全部检查」
却没查到分层文件。修法都写在上文。

## 对标与差距

本工程与真实开源企业系统对标（以 ERPNext 为例：3067 个 Python 文件 /
49.7 万行）：

| 维度 | 真实系统 | 本工程 |
|---|---|---|
| 领域组织 | 40+ 业务域目录 | 14 域，每域 5 层 |
| 文档类型 | `Document` 基类 + 生命周期钩子 | 结构体 + 构造辅助（无继承） |
| 金额处理 | `flt`（浮点） | **整数分**（更严格） |
| 事件机制 | 信号/钩子框架 | 事件总线（订阅-派发） |
| 规模 | 49.7 万行 | 6.2 万行 |

**差距**主要在基础设施：没有 ORM、没有数据库驱动、没有网络层——
这些是宿主环境能力，不是语言表达力问题。**语言层面能表达的部分，
本工程全部写出来了。**

## 可复现性

本工程随 `make 检查`（批量静态检查 examples 与 projects）一起被自动覆盖，
`sy 检查` 必须对它**零错误、零警告**；`主程序.sy` 必须**完整跑通退出码 0**。
这是「对外声明的数字必须有脚本能跑出来」这一约定的具体落实。
