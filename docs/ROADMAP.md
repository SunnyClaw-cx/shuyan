### 阶段 P3 · 性能（中期偏后）

> **前置进展（v0.2）**：基准套件已就位，实测结果——解释器在 10 万次量级下
> 耗时线性增长、无平方级爆炸（文本拼接已验证非 O(n²)）；
> 中文处理路径约为纯算术的 2 倍（函数调用开销），在解释器正常范围内。
> 后续优化有了**可对照的基线**，不必凭感觉改。

**决策点：性能路线**。三条候选路线，取舍如下：

| 路线 | 收益 | 成本 | 结论 |
|---|---|---|---|
| A. 树遍历 + 局部优化 | 1～3× | 低 | 先做（缓存解析结果、环境扁平化） |
| B. 字节码 VM | 5～15× | 中 | **推荐**（自研，无外部依赖，符合「完全自研」要求） |
| C. LLVM 后端 | 50×+ | 高（需 C++ 工具链） | 可选，视是否需要与系统语言竞争 |

**推荐路径**：A → B →（按需）C。先做 A 拿到即时收益，再做 B 建立自研 VM，
LLVM 保留为「需要极致性能时」的选项。

配套：`benchmarks/run_bench.py` 已提供七类基准（数值循环 / 函数调用 / 递归 /
文本拼接 / 中文处理 / 列表 / 映射），**编译期与运行期分开计时**，
后续每次优化都应与基线对照。

## 三、中文语言特有的坑 × 枢言的应对

中文编程语言普遍面临的四个坑，逐条对应枢言的处理：

| 坑 | 枢言的应对 | 状态 |
|---|---|---|
| **编码**：全程 UTF-8，全角符号 | 词法最前一步归一化；区分「意图明确」（`（）`→`()`）与「意图不明」（`《》`报错）；控制台强制 UTF-8 | ✅ 已解决 |
| **语法歧义**：中文无天然空格 | 三级字块单趟裁决；单字词禁止中缀切分；保留名整体保护 | ✅ 已解决（规则可预测） |
| **输入法切换**：来回切中英文体验差 | 全角/半角双写法；拉丁关键字别名（`let`/`if`/`fn`）；反引号逃生舱 | ✅ 已缓解 |
| **单字关键字吞噬高频词** | 7 个单字 A 类词（`令当若让设试请`）会前缀切坏 `当前`/`设备`/`设计`/`设置`/`试验` —— 加约束：仅当剩余部分是**多字**关键字时才融合，保住 `请假`/`让步` | ✅ 已解决（实测暴露） |
| **汉字名 + 拉丁后缀被截断** | `编码Base64` 的源码原文曾被截取成 `编码`，导致**所有**此类内置成员失效 —— 修复为吸收完尾段后再取原文，并加回归测试锁住 | ✅ 已解决（实测暴露） |
| **生态**：第三方库少 | 阶段 P4 的 FFI 为**关键**——不重复造全部轮子 | ⏳ 待做（明确优先级） |

## 四、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 单字联结词在无空格时不可切 | 部分自然写法不可用 | 规范显式声明边界；提供多字等价形式（`等于`/`属于`）；诊断给出改写建议 |
| 双端口语增加维护面 | 两套表面语法的测试成本 | 归一化到同一 AST，测试针对 AST 层，不做重复覆盖 |
| 生态起步晚 | 实用性受限 | FFI 优先，先能调用 C 库；同时把「中文优先」做成差异化优势 |
| 性能落后主流语言 | 不适合计算密集场景 | 分阶段（A→B→C）；明确适用场景定位（业务逻辑、文本处理、教学、自动化） |
