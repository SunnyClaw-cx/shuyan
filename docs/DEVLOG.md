## 2026-10-19 · v0.2 结构体、枚举与多文件工程

### 节点 1：结构体与枚举的落地路线（零新增关键字）

**决策过程**：最初想引入 `结构体` / `枚举` 两个新关键字。查证时发现
`枚举(列表)` **已是核心函数名**（返回 `[[下标, 元素]]`），若再作关键字会直接
撞车 —— 这不是可以调和的分歧，是必须绕开的硬冲突。

**最终路线**：复用既有 `类型` 关键字 + `{}` 花括号 + 结构体调用语法 + `.` 成员访问，
**一个关键字都不新增**。好处是三重的：
1. 不与任何既有名字冲突；
2. 语言的概念数不增加，用户只需知道 `类型` 一种声明形式；
3. 单趟扫描即可判定是结构体还是枚举（看花括号里有没有 `:`），不需要回溯。

**判定表**（SPEC §3.9.1）：

| 花括号内容 | 判定 |
|---|---|
| 全是 `名字: 类型` | 结构体 |
| 全是不带 `:` 的名字 | 枚举 |
| 混用，或为空 | 报 `D3019`（**不做统计猜测**） |

### 节点 2：枚举成员名必须按源码原文匹配

**问题**：`星期.一` 里的 `一`，词法上是**数词**，会被归一成 `1`。
若用归一值做成员匹配，`星期.一` 永远查不到 `一`。

**修法**：`Member.name_text` 保存**源码原文**，声明端与访问端
统一按原文匹配（与反引号逃生舱共用 `parser._name_text()` 这一个入口）。

**为什么强调「唯一入口」**：这正是项目铁律「同一语义两处实现必然分叉」的
典型场景 —— 声明端按原文、访问端按归一值，两边各写一次，必然对不上。

### 节点 3：真实程序逼出的缺陷（本版核心）

**做法**：写一个三文件的多文件样例工程 `projects/库存管理/`
（领域模型 / 库存服务 / 主程序），定义类型 → 构造 → 流转 → 汇总 → 预警 →
CSV 导出，六步真实业务链路，**故意包含「库存不足」与「状态未完成」两个分支**。

**结果**：程序跑到第三步就崩了，暴露出 6 个**既有缺陷** —— 全都是
「写 demo 永远碰不到、写真实程序必然撞上」的那一类。逐个记录：

#### 缺陷 A：汉字名 + 拉丁后缀的源码原文被截断（**影响面最大**）

**症状**：`编码.编码Base64("你好")` 报「模块里没有『编码』这个成员」。
打印记号发现：`text="编码"`、`value="编码Base64"` —— **原文与值不一致**。

**根因**：`lexer._han_block` 在**吸收拉丁尾段之前**就取了 `raw_text`
（`self.raw[raw_start:self.pos]`）。对 `编码Base64` 而言，此时 `pos` 还停在
汉字 `编码` 之后，于是原文只有两字，而随后拼接的 `value` 是完整的。

**为什么影响面大**：凡「汉字名 + 拉丁后缀」的记号**全部**中招 ——
`编码Base64`、`解码Base64`、`导出CSV`… 全部查不到。而且报错文案指向
十万八千里外（先是「空不是函数」，后是「模块里没这个成员」），
**症状与根因的连线极长**，是最难定位的一类。

**修法**：把 `raw_text` 的取值移到**吸收完所有尾段之后**。

**回归测试**：新增分组「词法·汉字名加拉丁后缀」，同时断言
① 切分唯一；② `text == value`（原文完整）；③ 端到端能命中。

#### 缺陷 B：七个单字 A 类关键字前缀切坏高频词

**症状**：`系统.当前目录` 被切成 `系统.` + `当`(while) + `前目录`。

**根因**：`当` 是单字 A 类引导词，前缀匹配命中后即融合切分。
但凡以 `当` 开头的词（`当前`）都会中招。同类的还有
`令 当 若 让 设 试 请` 会切坏 `设备清单`、`设计图纸`、`设置参数`、
`请求登记`、`试验记录`、`请假`。

**修法**：新增 `A_SINGLE` 约束（与既有的 `C_SINGLE` 同口径）：
单字词**仅当剩余部分是「多字关键字」时**才融合切分。这样保住
`请假`（剩余是单字 `假`）、`让步`（剩余是单字 `步`，非关键字），
同时不破坏 `若成立` 这类融合写法。

#### 缺陷 C：内置函数收具名参数被完全静默丢弃

**症状**：`输出(甲 是 5)` **既不输出、也不报错**。

**根因**：`输出` 签名为可变参数，具名参数躲过了参数个数检查，
又在运行期被丢弃。

**为什么这是最严重的一类**：与项目铁律「静默失败比报错危险」**直接冲突**。
用户写错了代码，程序若无其事地继续跑 —— 这种错误可能在几千行之后才以
完全无关的症状爆发。

**修法**：新增 `_check_stray_kwargs()`，内置函数收到具名参数一律报 `D3007`。

#### 缺陷 D：用户函数具名参数不计数

**症状**：`问候(名字 是 "老李")` 误报「需要 2 个参数，给了 0 个」。

**根因**：语义层只数 `len(node.args)`，没算 keyword 参数。

**修法**：`_check_user_arity` 改签名，把 kwargs 计入总数，并校验未知具名参数；
运行期 `_call_shuyan` 同步改为 `bound = len(args) + len(kwargs)`。
（**语义层与运行期必须同序** —— 又一次落实这条铁律。）

#### 缺陷 E：成员名被归一化后查不到

**症状**：`文本.重复("a", 3)` 报「『空』不是函数，不能调用」。

**根因**：`重复` 是关键字（`loop`），`.重复` 的成员名被归一成 `loop`，
查不到成员 → 静默返回空 → 空被当函数调用 → 报错在十万八千里外。

**修法**：`_eval_Member` 与 `_expr_Member` 统一改用 `key = node.name_text or node.name`；
并对模块命名空间的缺失成员**明确报错**（此前是静默返回空）。

#### 缺陷 F：类型名当值使用拖到运行期才报

**症状**：`输出(点)` 在运行期才报错。

**修法**：新增 `_report_bare_type_use`，在**编译期**报 `D3005`
「类型名不能当作值使用」，并给出「是否想用 `类型名(...)` 构造」的建议。

### 节点 4：跨模块能力的三个连锁缺陷

多文件工程落地时，跨模块调用又暴露三个缺陷：
① 子解释器未传 `analyzer`，导致跨模块枚举成员表为空；
② 子解释器 `env` 未跟随 `global_env` 替换，语句写进旧环境、导出全空；
③ 语义层拒绝 `.sy` 文件引入，而运行期支持 —— **编译期与运行期口径不一致**。

②③ 促使将「候选路径与导出规则必须同口径」明确写进 SPEC §3.8.1。

### 节点 5：性能基准确立基线

**做了什么**：`benchmarks/run_bench.py`，七类用例，**编译期与运行期分开计时**，
取中位数（解释器受调度与 GC 干扰，均值易被离群值拉偏）。

**实测结果**（规模 10 万量级）：

| 用例 | 规模 | 编译期 | 运行期 |
|---|---|---|---|
| 循环·数值 | 100000 | 297 µs | 530 ms |
| 函数·调用 | 50000 | 340 µs | 351 ms |
| 递归·斐波那契 | 20 | 312 µs | 147 ms |
| 文本·拼接 | 20000 | 284 µs | 113 ms |
| 中文·字符计数 | 100000 | 406 µs | 1.17 s |
| 列表·追加遍历 | 100000 | 458 µs | 830 ms |
| 映射·哈希查找 | 50000 | 526 µs | 777 ms |

**三条结论**：
1. 10k → 100k 耗时约 10 倍，**线性增长，无平方级爆炸** ——
   文本拼接已验证不是 O(n²)（这是最需要警惕的一类性能陷阱）。
2. 中文处理约为纯算术的 2 倍，属**函数调用开销**（每次多调一层
   `长度`/`显示宽度`），在解释器的正常范围。
3. 编译期稳定在数百微秒，**远小于运行期** —— 印证了「只看总耗时会启动开销
   掩盖执行效率」这一判断。

### 节点 6：CLI 只处理第一个文件（**静默遗漏**）

**症状**：`sy 检查 examples/*.sy`（5 个文件）只输出 1 行 `✓`，
却让人以为全部通过。`sy 运行`、`sy 格式化` 同样只取 `args[0]`。

**为什么严重**：Makefile 的 `检查` 目标、CI 的静态检查步骤、
文档里的命令**全都**写成 `examples/*.sy` 形状 —— 也就是说，
自动化检查实际上**只验证了一个文件却报告通过**。
这比「检查没写」更危险：它制造了虚假的安全感。

**修法**：`检查` / `格式化` / `运行` 全部改为处理**全部文件参数**；
`运行` 顺序执行、任一失败即返回非零；`格式化` 非写入模式加文件分隔标注。

**教训**：「只看 `args[0]`」在 shell 世界里几乎总是错的 ——
glob 展开是常态，不是特例。

### 节点 7：格式化器破坏源码（**严重**）

**症状**：`sy 格式化` 把 `n <= 1` 改成 `n < = 1`，程序直接语法错误。
所有多字符运算符全部中招：`==` → `= =`、`+=` → `+ =`、`>=` → `> =`。

**为什么严重**：格式化器的契约是**只改外观、不改语义**。
把能跑的程序格式化坏，比不格式化严重得多 —— 而且它会在提交前批量
重写整个仓库的源码，一次事故污染全部文件（本次已实际写坏 `斐波那契.sy`）。

**根因**：`_is_complete_operator` **只向前检查、不向后检查**。
补空格的循环按 `("==", "!=", "<=", ...)` 顺序处理多字符运算符，
每轮都对**整个字符串**重新扫描。处理完 `==` 后字符串已是 `a == b`，
轮到单字符 `=` 轮次时：

- 首个 `=`：后面是 `=` → 正确跳过；
- **第二个 `=`**：后面是空格 → 被判为独立运算符 → 补空格 → `= =`。

**修法**：补上**向后检查** —— 本字符若紧跟 `=!<>+-*/%` 之一，
则它是多字符运算符的后半部分，不得独立处理。

**为什么既有测试没抓到**：格式化测试只用了 `>`（单字符），
**恰好绕开**了所有多字符运算符。这是「测试用例不覆盖真实写法 =
虚假的安全感」的典型案例 —— 于是新增分组
「格式化器·不得破坏多字符运算符」，覆盖 8 个多字符运算符 +
单字符补空格功能 + **幂等性**。

### 节点 8：语义层两处实现分叉（`callee.name` vs `name_text`）

**症状**：`sy 运行` 能跑通 `文本.重复`，`sy 检查` 却报
「模块『文本』里没有『loop』这个成员」。

**根因**：成员名的「取源码原文」逻辑在语义层有**两处**：
`_expr_Member`（成员访问）与 `_expr_CallTarget`（模块成员**调用**）。
前者已改用 `name_text`，后者仍用归一名 `callee.name` ——
`重复` 归一后是 `loop`，于是报错里带着 `loop` 这个内部名字。

**修法**：`_expr_CallTarget` 的模块成员分支同步改用
`key = callee.name_text or callee.name`。

**教训**：这正是项目铁律「**同一语义两处实现必然分叉**」的第 N 次应验。
本次是先修了访问路径、漏了调用路径，两条路径的差异只在
「后面有没有 `()`」—— 一个极易被忽略的分界。

### 节点 9：检查与运行的模块解析基准不一致

**症状**：`sy 运行 projects/库存管理/主程序.sy` 正常，
`sy 检查` 同一文件却报「找不到模块『领域模型』」。

**根因**：本机模块的解析基准是「主脚本所在目录」（SPEC §3.8.1）。
`sy 运行` 创建 `StdLib(base_dir=脚本目录)`，而
`sy 检查` 走 `lint_source()`，内部新建的 `StdLib()` 用的是默认
`base_dir=os.getcwd()` —— **编译期与运行期口径不一致**。

**修法**：`lint_source` 增加 `filename` 参数，据此设置 `base_dir`；
CLI 调用时传入路径。

**教训**：又一次「两处实现分叉」，只是这次分叉在**工具链**而非语言核心。

## 2026-10-19 · v0.2.1 高阶函数、错误恢复与表示统一

### 动机：先诊断根因，再动手

v0.2 发布后做了一次**成熟度自检**：把项目当作第三方交付物来审视，
找出「成熟项目不该有、而当前实现确实存在」的硬伤。

采用「先探测、后动手」的顺序 —— 不加没经过验证的功能，因为那属于
「用新增量掩盖旧问题」。自检结果如下：

| 自检项 | 实测结果 | 判断 |
|---|---|---|
| 错误恢复 | `定义 乙 == 2` 一行报 **4 条**错，且污染后续行 | ⛔ 硬伤 |
| 高阶函数 | 标准库**一个都没有**；写真实程序只能手写 `当` + `入列` | ⛔ 硬伤 |
| 输出表示 | 同一文本值在列表 `[甲, 乙]`、在映射 `{'甲': 1}` | ⛔ 不一致 |
| REPL / JSON / CSV | 均无 | 记入路线图 |

前三条立即开工（即本版三个主攻点）。

### 节点 1：错误恢复 —— 从「四倍报错」到「一行一错」

**症状**：一行 `定义 乙 == 2` 产生 4 条诊断，且后续**本来正确**的行也被报错。

**根因**：解析器遇错后**没有同步恢复点**。`_parse_call` 报「参数列表未闭合」
之后，调用方继续按「参数还在后面」的假设往下解析，于是同一根因被反复报告，
并一路吃掉了后续记号。

**修法**（三处配合，缺一不可）：

1. **行级恐慌恢复** `_sync_to_next_line(mark)`：进入语句时记下错误计数；
   语句结束时若计数增加，丢弃本行剩余记号、跳到下一行行首。
2. **`_guard_trailing_tokens` 重写**：原实现只拦截「像值」的记号，
   现在拦截**任何**残余记号 —— 但若本条语句**已报过错**则不再补刀
   （`_stmt_mark` 判断），避免二次报错。
3. **在调用与表达式处设卡**：参数位置若出现「语句起始关键字」，
   基本可判定是上一行漏了右括号 ⇒ 报一条「未闭合」并置
   `_suppress_followup`，抑制后续衍生报错。

**验证**（`test_error_recovery_one_per_line`，5 类场景）：
单行一错 · 不级联 · 两处独立错误报两条 · 未闭合括号只报一条 ·
正常程序零报错。

**设计取舍**：恢复点选「下一行行首」而非「下一个分号」。枢言以换行作
语句终止（SPEC §2.7），分号非必需，以分号为恢复点会漏掉大量情形。
**宁可保守** —— 放弃同行后续的发现，也不制造错误洪水。

### 节点 2：高阶函数 —— 回调宿主是绕不开的一环

**验证前置**：先确认枢言函数确为一等公民（`应用(平方, 5)` 输出 25，
匿名函数 `函数(x) 返回 x * 2 结束` 亦可用）。结论：可行。

**关键难点**：内置函数**拿不到解释器上下文**。枢言函数执行需要作用域链、
调用栈、返回信号（`ReturnSignal` 以异常传递），这些都在解释器手上。
内置函数自己无法执行枢言函数。

**修法**：**回调宿主注入**。解释器初始化时把自己的调用能力交给标准库
（`self.stdlib.callback = self._invoke_shuyan`）；内置函数经
`StdLib._invoke(fn, args, where)` 使用。

**过程中修掉的两个自身缺陷**：

- **`_invoke` 两条路径混用**：宿主函数（如 `绝对值`）也是 `callable`，
  曾与枢言函数走同一分支，会在 `_call_shuyan` 取 `fn.params` 处炸出宿主异常。
  → 分开：`ShuyanFunction` 走 callback，其余 `callable` 直接调用。
- **`error(...)` 写成 `return`**：`error()` **返回**异常对象，必须 `raise`。
  写成 `return` 会让「非函数参数」静默通过 —— 又一个静默失败。

**真值判断统一**：新代码误用了私有 `_truthy`（未定义），而文件里已有
`values.is_truthy`。**没有**另造别名（那正是「同一语义两处实现」）——
直接复用同一份，确保「标准库认为假」与「语言内 `如果` 认为假」永远一致。

### 节点 3：容器输出表示 —— 三份实现收敛为一份

**症状**（由高阶函数测试撞出）：

```shuyan
输出({"甲": 1})        # {'甲': 1}   ← 键带单引号
输出(["甲", "乙"])     # [甲, 乙]    ← 元素不带引号
```

同一文本值，在两种容器里长得不一样。

**根因**：容器渲染**写了三份**：
列表在 `display` 里手写一份、映射在 `ShuyanMap.__repr__` 写一份、
结构体在 `ShuyanStruct.__repr__` 再写一份。其中映射的键用了 Python 的
`{k!r}` —— 那是 **Python 的表示**，不是枢言的表示，单引号就是这么来的。

**修法**：收敛为**唯一容器渲染实现** `values._render(value, elem)`。
容器结构只写一份；`elem` 决定元素用哪种口径：

| 口径 | 元素文本 | 用途 |
|---|---|---|
| `_show_text`（不加引号） | `甲` | 用户输出路径（`display`｜`输出`｜`转文本`） |
| `_show_repr`（加引号） | `"甲"` | 调试表示（Python 层 `__repr__`） |

**连带修正**：`test_struct_text_nested` 原期望 `员工{姓名: "陈工"}`。
按新口径应不带引号 —— **这不是「改测试迎合实现」**，而是原期望本身
自相矛盾：`输出(甲.姓名)` 得 `陈工`，`输出(甲)` 却得 `姓名: "陈工"`，
同一个值取出来与整体打印不一致。SPEC §6.2.2 已把该口径写成硬性约束。

### 节点 4：把「没有的」也写进文档

本项目遵循一条原则：**不要让人误以为有那些东西**。据此在
README、SPEC、ROADMAP、CHANGELOG 四处如实声明实现边界：

| 维度 | 如实写法 |
|---|---|
| 执行方式 | **解释器**；**没有**字节码 VM、**没有** JIT（ROADMAP 阶段 P3） |
| 性能定位 | 「可用」非「最快」；不追求零开销抽象 |
| 类型系统 | **保守推断**，只在能推的地方推；**不是** HM 类型推导，**不是**借用检查 |
| 交互环境 | **无 REPL**（只能运行源码文件，ROADMAP 阶段 P2） |
| 调试 / 依赖 | **无调试器**（P2）· **无包管理器**（P4） |

SPEC 新增 §10.1「实现现状与已知限制」表与 §5.4.1「推断能力边界」
（明确列出**能推断的 6 类**与**推不出的 4 类**）。

**理由**：评估者按文档的承诺来判断工具。文档若暗示存在而实际不存在，
信任损失远大于功能缺失本身。**把「没有的」写清楚，与把「有的」写清楚同等重要。**
凡「运行能过、检查报错」的症状，第一反应就该是查两边的入口参数是否同口径。

## 2026-10-19 · v0.1 从零到全链路可用

### 节点 1：规范先行（SPEC.md 冻结）

**做了什么**：在写任何代码前，先冻结 `docs/SPEC.md`——词法、语法、类型、语义、
诊断、格式化风格、EBNF 全量定义。

**为什么这样做**：中文编程语言的失败案例里，多数是从「先写个能跑的 demo」开始，
语义一变再变，最后规范无法收敛。规范先行是「可测试语言」与「玩具」的分界线。

**规范内被修订的设计**（写规范过程中自己发现的矛盾）：
- 初稿把切分算法定义为「两级（紧贴/独立）」→ 发现 `若年龄不小于18` 这类
  无空格写法会失效 → 改为**三级（前缀/后缀/中缀）**。
- 初稿把全角逗号 `，` 一律归一为列表分隔符 → 发现自然汉语里 `若 甲 大于 3，那么`
  的 `，` 是句读停顿 → 增加「句读逗号」规则。
- 初稿承诺 `2 的 10 次方` 作幂运算 → 实测否决（见节点 5）。

### 节点 2：诊断系统与词法层

**新增文件**：`source.py`（显示宽度）· `diagnostics.py`（诊断与渲染）·
`keywords.py`（三类关键字）· `names.py`（保留名）· `lexer.py`（词法器）

**关键实现**：词法步骤顺序被定为
`保留名整体保护 → 口语变体 → 整体关键字命中 → 中文数词 → A类前缀 → C类后缀
→ C类中缀 → 软助词 → 整体标识符`。
**顺序即正确处理**——先匹配长词、先保护保留名，才能避免误切。

**本节点修掉的缺陷**：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `订单_ID` 被切成 `订单` + `_ID` | 混合标识符未处理 | 汉字块读完后续接 `_`/拉丁段 |
| 2 | `甲_乙` 仍被拆开（下划线在块**之后**） | 只检查了块内下划线 | 增加「流中下划线」判定分支 |
| 3 | `类型名` 被切成 `类型` + `名`，内置函数失效 | 关键字前缀撞内置名 | 新增 `names.py` 保留名整体保护 |
| 4 | `十`、`十亿` 解析失败 | 只有单位没有数字，`seen_any` 未置位 | 单位分支同时置位 `seen_any` |
| 5 | `0.0` 被前导零检查误伤 | 前导零检查未区分整数/小数 | 限定 `not is_float` |

### 节点 3：AST 与语法分析器

**新增文件**：`ast_nodes.py` · `parser.py`

**关键设计**：**双端口语/书面语在词法层就完成归一**——白话的 `若`/`设`/`说`
在词法阶段已是 `if`/`let`，解析器因此无需为白话写第二套语法。
这是「白话可编程」成本可控的根本原因。

**本节点修掉的缺陷**：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 6 | `若 甲 不小于 18，那么` 报语法错误 | 句读逗号未忽略 | 新增 `_skip_pause()` |
| 7 | `设 甲 是 5，` + 换行 后仍报错 | 跳逗号后停在换行上，未交替清理 | 逗号与终止符**交替**清理至稳定 |
| 8 | `遍历 [1,2,3] 中的每个 x` 报错 | 白话遍历只支持「变量名在前」 | 按第二记号形态分流两种读法 |
| 9 | `2 的 10 次方` **静默算成 2** | 剩余记号被丢弃，无守卫 | 新增 `_guard_trailing_tokens()` + 参数内检查 |

> **缺陷 9 是本项目最重要的一次修复**。静默丢弃比报错危险得多——
> 用户会以为语言算错了。现改为明确报错并指向根因字符 `的`，附改写建议。

### 节点 4：语义分析器与解释器

**新增文件**：`values.py` · `errors.py` · `builtins.py` · `semantic.py` · `interpreter.py`

**关键设计**：
- **控制流用异常信号**（ReturnSignal/BreakSignal）传递，避免每层求值都判空；
- **异常模型分层**：枢言 `抛出` 可被 `捕获`，宿主 bug 直接冒泡——
  否则「用户程序的异常」与「实现缺陷」无法区分；
- **类型名是中文的**：`类型名(1)` 返回 `"整数"`，报错才读得通。

**本节点修掉的缺陷**：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 10 | `总分 += 分数` 报「运算符 / 需要数字，实际是空」 | **同一语义两处实现**：`+` 的文本拼接只写在二元求值里，`_apply_op` 落空 | 收敛为唯一入口 `_add()`，`+` 与 `+=` 同口径 |
| 11 | 字符串内 `你好，世界！（测试）` 被改成半角 | 全角归一化未排除字符串内容 | 循环内取 `raw_ch`；仅插值**表达式**用归一化文本 |
| 12 | `重复 甲 从 1 到 5` 只跑了 4 次 | 区间闭合性未定义 | 定义闭区间并写入 SPEC §3.5 |
| 13 | `长度(1)` 运行期才报错 | 内置函数未做参数类型静态校验 | 新增 `CORE_PARAM_TYPES` / `MODULE_PARAM_TYPES` |
| 14 | 用户定义 `请 求和(...)` 后仍按内置签名报错 | 语义层与运行期**查询顺序不一致** | 统一为「用户定义优先」，两侧同序 |
| 15 | `真 是 1` 被编译期拦下 | 语义层过严，与 SPEC §4.6 冲突 | 放行（规范规定返回假值，是刻意设计） |

### 节点 5：工具链与测试

**新增文件**：`formatter.py` · `linter.py` · `cli.py` · `tests.py` · `sy.py` · `examples/*.sy`

**关键设计**：
- 格式化器**基于行**而非 AST 重排——AST 重排会丢注释，中文源码注释密度高；
- Lint 区分「代码区」与「字符串内部」，避免误报；
- 测试分五类：词法切分 / 语义执行 / 负例报错 / 标准库中文处理 / 格式化器。

**本节点修掉的缺陷**：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 16 | W4204 被标为「运行时错误」 | 类别名从码号第二位推断，`W` 开头误入 D 类映射 | 警告码一律标为「代码提醒」 |
| 17 | 字符串内全角括号触发风格警告 | Lint 未排除字符串内容 | 新增 `_outside_strings()` |
| 18 | 运行警告被渲染成「运行时错误」 | 警告与运行期诊断混在同一渲染流 | CLI 分离渲染，仅报条数 |
| 19 | **注释里**的全角括号也被警告 | 只排除了字符串，未排除注释 | 新增 `_strip_comment()`，仅对代码区提示 |

## 缺陷统计与归类

v0.1 共发现并修复 **19 个缺陷**。按根因归类：

| 类别 | 数量 | 说明 | 教训 |
|---|---|---|---|
| **中文切分/编码** | 6 | 混合标识符、保留名、数词、全角归一化 | 中文优先的设计，每个决定都要实测 |
| **同一语义多处实现** | 2 | `+=` 落空、查询顺序不一致 | 收敛为唯一入口；两处实现必然分叉 |
| **静默失败** | 2 | 剩余记号被丢弃、缩进警告误导 | 静默错误比报错危险，必须设守卫 |
| **规范-实现不一致** | 2 | 区间闭合性、`真 是 1` | 以规范为准，实现服从规范 |
| **诊断呈现** | 4 | 类别名、字符串误报、注释误报、渲染混杂 | 报错说错类别 = 把人往错方向带 |
| **前端语法覆盖不全** | 3 | 白话遍历、句读逗号、无括号调用 | 白话端每个写法都要有测试 |

**最值得记住的一条**：缺陷 10（`+=` 落空）与缺陷 14（查询顺序不一致）是同一类——
**同一语义存在两处实现时，必然分叉**。修复方式都不是「改其中一处」，
而是**收敛为唯一入口**。

### v0.2 / v0.2.1 追加缺陷（累计 34 个）

| 类别 | 数量 | 代表缺陷 | 教训 |
|---|---|---|---|
| **错误恢复** | 1 | 一行报 4 条错并污染后续行 | 恢复点必须显式设置，否则同一根因被反复报告 |
| **同一语义多处实现** | 4 | 容器渲染三份 · 真值判断两份 · `_invoke` 分支混用 · 成员名 `name` vs `name_text` | 每次「收敛为唯一入口」都消灭一整类失败 |
| **静默失败** | 3 | `error(...)` 未 `raise` · CLI 只处理首个文件 · 模块成员缺失静默返回空 | 静默失败比报错危险，必须设守卫 |
| **源码原文截断** | 1 | `编码Base64` 的 `text` 被截成 `编码` | 汉字名 + 拉丁后缀是中文语言的固有风险点 |
| **格式化器破坏语义** | 1 | `<=` → `< =`，`==` → `= =`，**实际写坏过源码** | 格式化器只改外观；多字符运算符必须双向检查 |
| **规范-实现不一致** | 1 | `sy 检查` 与 `sy 运行` 模块解析基准不同 | 编译期与运行期必须同口径 |
| **文档过时** | 1 | 已实装模块被标为「路线图」 | 文档滞后与功能缺失同样损伤信任 |

**新增的一条**：**同一语义在容器渲染上写了三份** —— 列表一份、映射一份、
结构体一份，且映射的键借用了 Python 的 `{k!r}`。这与缺陷 10 / 14 同族，
但更隐蔽：它不是「算错」，而是「**看起来对、跨容器对不上**」。
防线是**输出表示也要有唯一实现**，并且测试要覆盖**跨容器的一致性**，
而不只是单容器正确。
