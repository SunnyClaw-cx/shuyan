## 2026-10-20 · 标杆驱动：用「别的语言也能写的项目」反推语言缺口（v0.4.1）

### 起点：规模测试测不出表达力

v0.3 已经回答「十万行能不能跑」。但规模只证明**跑得动**，证明不了
**表达力够不够**。于是换一种打法：

1. 挑一个**任何通用语言都能实现**的企业系统 —— 大厂级中台（主数据、
   采购、销售、库存、生产、质量、财务、人力……）；
2. **用枢言从头把它写出来**（不是改写已有的，是真写）；
3. 写作过程中凡遇到「写不出来 / 写出来是 bug / 写法别扭」的地方，**记下来**；
4. 拉一个真实开源工程**横向对比**，看别人怎么解决同一问题；
5. 把差距转成语言的改进项 —— **修完再跑一遍，真跑通才算数**。

**为什么这条路不可替代**：规模测试是被动的（跑得动就行），
标杆驱动是主动的（必须真的把一件事做成）。很多缺口只有「真去写」才撞得上。

### 节点 1：写生成器，先撞上自己的词法规则

用 `tools/gen_platform.py` 批量生成 14 域工程。**开工第一小时全在撞词法**：

| 写下的名字 | 实际切分 | 现象 |
|---|---|---|
| `轮次` | `轮` + `次` | 报 `D3019`「混用了两种写法」 |
| `审批中` | `审批` + `中` | 枚举成员被切开 |
| `某命中` | `某命` + `中` | 同上（C 类单字后缀要求前缀 ≥ 2） |
| `类型操作者` | `类型` + `操作者` | 报 `D3006`「函数名不能使用关键字」 |
| `全局审计记录` | `全局` + `审计记录` | 报 `D3006`「变量名不能使用关键字」 |

这些**都不是语言缺陷** —— 是 SPEC 明文规定且已冻结的切分规则
（§2.4 三级字块裁决 + 数词单位词优先）。正确做法是**改生成器**：
`轮次 → 轮数`、`类型操作者 → 取操作者种类`、`全局审计记录 → 审计留痕`。

**但由此发现一个真问题**：`轮次` 被切分时报的是 `D3019`
「混用了两种写法」——**报错点 ≠ 真因点**。真因是「标识符被数词规则切开」，
用户看到的是「结构体写法混用」，方向完全错。这符合项目既有规范
「报错点 ≠ 真因点时必须在真因处留提示」的缺口，记入待办。

### 节点 2：`参数: 类型` 只写不查（对标 ERPNext 逼出）

先拉真实项目做对比。GitHub 直连受限，改用 gitee 镜像成功克隆
**ERPNext**（Frappe 体系的企业资源计划系统，3067 个 Python 文件 / 49.7 万行）。

对比中最刺眼的一条：

| 维度 | ERPNext | 枢言 |
|---|---|---|
| 通用流程复用 | `Document` 基类 + 生命周期钩子，`validate` 被重写 **1454 次** | 高阶函数（回调）可等价表达 |
| 金额精度 | `flt`（浮点） | 整数分（更严谨） |
| 参数约束 | 运行时 `ValidationError` | `参数: 类型` —— **但只写不查** |

验证「只写不查」：

```shuyan
请 通用(单据, 回调: 函数)
    返回 回调(单据)
结束
定义 甲 = {"编号": "X"}
输出(通用(甲, 123))      ← 传了整数，不是函数
```

`sy 检查` 报 **0 错**，`sy 运行` 崩。再试 `请 问候(名字: 文本)` 后调
`问候(123)`，同样检查通过。

**这不是「缺功能」，是给了假的安全感** —— 用户以为标了类型就有保障，
实际一行检查都没跑。这与本项目铁律「编译期与运行期必须同口径」直接冲突。

**修法**：新增 `Analyzer._check_call_arg_types`，复用既有的 `can_assign`
（SPEC §5.4）判兼容，**不重造比较逻辑**（否则又是一处同语义两实现）。
口径保守，宁可漏报不可误报：

- 未标注（`任意`）→ 放行
- 实参推不出（`任意`）→ 放行（**推不出 ≠ 类型错**）
- §5.4 拓宽（`整数 → 文本`）→ 放行
- 只对「两侧都能推出且确实不兼容」报 `D3004`
- 回调只校验「是函数」，**不比签名**（协变属 v0.5，不装懂）

**踩到的坑**：第一版以为 `问候(123)` 该报错，实测没报，一度以为守卫没生效。
追下去才发现 `can_assign(整数, 文本)` 返回 `True` —— `整数 → 文本` 是
SPEC §5.4 明文允许的拓宽。**是我的预期错了，不是实现错了。**
教训：写检查前先读规范里已有的兼容规则，别按直觉臆断。

### 节点 3：模块解析回退到 CWD（违反已冻结的 SPEC）

生成器做的分层工程「逐文件独立检查」时报「找不到模块」，但整工程检查通过。
写 `tools/probe_layout.py` 做**受控实验**：固定主脚本、**只切换进程 CWD**
（工程根 vs 空白目录），同一份代码。

结果：**检查结论随 cwd 变化**。

**根因**：`StdLib.resolve_module_file` 的候选路径里带了两条
**回退到进程 CWD** 的路径。而 SPEC §3.8.1 明写：

> 路径基准 = **主脚本所在目录**（不以当前工作目录为准）

回退让一个**违反规范**的实现看起来能跑。**修法**：改成
「主脚本目录 → 逐级上溯父目录（≤64 级）→ 相对 CWD 兜底」，
去掉两条裸 CWD 回退。修复前后 **2 项失败 → 6/6 全过**。

### 节点 4：引入含错模块 → 用户看到 Python 堆栈

`sy 检查` 引用语法错模块的主程序时，用户看到 `Traceback`。
**宿主崩溃是诊断体系最大的漏洞** —— 用户一旦看到 Python 堆栈，
所有精心设计的中文诊断全部失效。

**根因**：`Analyzer._import_module_file_inner` 用 `Parser.parse()`
（一见诊断即 `raise`），调用处没接住。**修法**：改用 `parse_recovering()`
拿 `(部分 AST, 诊断)` 并把诊断回流到父分析器。
修复前后 **2 项失败 → 3/3 全过**。

### 节点 5：同一位置两条诊断，第一条把人带偏

`转文本(甲 是 乙)` 报**两条** `D3007`：

```
函数「转文本」需要 1 个参数，但这里给了 0 个。    ← 第一条：把人引向「去补参数」
内置函数「转文本」不支持具名参数，参数「甲」会被忽略。  ← 第二条：才是真因
```

具名参数的语义决定「位置参数必为 0」是**必然后果**，
而 `_check_arity` 只看 `len(node.args)`。**修法**：内置核心函数与内置模块成员
两条路径，**只要出现具名参数就跳过个数检查**（SPEC §8.2.5 衍生报错抑制）。

### 节点 6：具名参数守卫对关键字成员名失效（假通过）

`文本.重复(甲 是 乙)` —— `检查` 报 0 错，**运行必崩**，
且错误信息泄漏宿主函数名 `StdLib._repeat_text()` 与英文形参 `'text'`/`'times'`。

**根因**：守卫用归一名 `callee.name`。`重复` 是关键字，归一名是 `loop`，
在成员表里查不到 ⇒ **守卫整条失效**。违反本项目铁律
「成员名一律取源码原文」。**修法**：改用 `callee.name_text or callee.name`。

### 节点 7：真跑一遍

工程真正落地为：**14 域 × 12 实体 × 5 层 + 7 框架模块 + 主程序**。

```
生成完成：78 个文件，62134 行
  域 14 · 实体 168

$ sy 检查 全工程   → 78 文件零错误、零警告
$ sy 运行 主程序.sy → 退出码 0
  自证一：各域实体数范围 6 ~ 6        装载一致：真
  自证二：状态统计覆盖 84 条记录
  仓储自证：每域删除行数合计 = 14（应为域数）
```

**收尾四处修正**（前两条是「声明数字必须与实测同口径」，后两条是
「声明与实际不符」——一处说「每域五层」却有一层不跑，一处说「全部检查」
却没查到分层文件）：

1. **超宽引入行**：补全引入会把一个域的 12 个实体堆成一条超长引入行，
   触发 W4202。修法是按**显示宽度**折行 —— 宽度算法**复用语言自身的
   `shuyan.source.display_width`**，不在生成器里另写一份（另写必然分叉）。
   折行安全的前提是「同一模块允许重复按名引入」，已在源码实测确认。
2. **行数口径**：原计数 `count("\n") + 1` 对「末尾已有换行」的文件恒多加 1，
   78 个文件虚报 78 行（工具报 61707、`wc -l` 报 61629）。改为生成时统一
   补末尾换行、按换行符个数计数 ⇒ 工具 / `wc -l` / 逻辑行数三处一致，均为 62134。
3. **仓储层是死代码孤岛**（14 文件约两万行）：无模块引入它，递归检查也
   覆盖不到 —— 实测「服务层注错能报出、仓储层注错报不出」即证据。
   真因有两个：① 仓储导出名**不带域前缀**，而实体名会跨域重名
   （`财务报表` 同时在财务域与报表域、`物料清单` 同时在生产域与研发域），
   导致 14 个仓储模块无法被同一主程序引入；② 主程序从未调用仓储。
   修法：导出名一律带域前缀 `{域}_新增X` / `{域}_找X` …；装载改走 `新增`；
   新增「仓储存取演示」段对每域首实体走一遍「查 → 筛 → 计数 → 改 → 删」。
   修后实测：仓储注错会被主程序检查连带报出 ⇒ **它确实在依赖链上了**。
4. **批量检查漏分层工程**：`Makefile` 的 `检查` 原为
   `examples/*.sy projects/*/*.sy`，只匹配一层，企业平台的分层文件
   （`projects/*/*/*.sy`）不在范围。补上第三段 glob 后共 99 文件全绿。

**自证第三条（仓储自证）**：每个域删除一行后列表必须恰好少一行
（合计 = 域数）。这条同时验证「仓储确实在跑」与「整体替换语义正确」——
测第一版时正因为漏了赋值（`更新` 返回新列表却没接），名称与状态**原样不变**，
加上这条不变量才当场暴露。

**两条自证不变量**是关键设计：工程自己核对自己的不变量（装载数一致、
统计覆盖完整），跑一遍即知成不成，不需要人眼核对数字。

### 本轮四缺陷的共性

四条缺陷（只写不查、CWD 回退、宿主堆栈、守卫失效）**全部**属于
同一类：**「看起来能跑」**。它们不会让程序当场报错，
只会让用户在**错误的信任**上继续往前走。

这正是本项目反复强调的那条：**静默的错误比响亮的错误危险得多。**
标杆驱动的价值就在于 —— 只有真去写一个**本来该能写成**的项目，
才会撞上这些「看起来没问题」的地方。

## 2026-10-19 · v0.2 结构体、枚举与多文件工程

### 节点 1：结构体与枚举的落地路线（零新增关键字）

**决策过程**：最初想引入 `结构体` / `枚举` 两个新关键字。查证时发现
`枚举(列表)` **已是核心函数名**（返回 `[[下标, 元素]]`），若再作关键字会直接
撞车 —— 这不是可以调和的分歧，是必须绕开的硬冲突。

**最终路线**：复用既有 `类型` 关键字 + `{}` 花括号 + 结构体调用语法 + `.` 成员访问，
**一个关键字都不新增**。好处是三重的：
1. 不与任何既有名字冲突；
2. 语言的概念数不增加，用户只需知道 `类型` 一种声明形式；
3. 单趟扫描即可判定是结构体还是枚举（看花括号里有没有 `:`），不需要回溯。

**判定表**（SPEC §3.9.1）：

| 花括号内容 | 判定 |
|---|---|
| 全是 `名字: 类型` | 结构体 |
| 全是不带 `:` 的名字 | 枚举 |
| 混用，或为空 | 报 `D3019`（**不做统计猜测**） |

### 节点 2：枚举成员名必须按源码原文匹配

**问题**：`星期.一` 里的 `一`，词法上是**数词**，会被归一成 `1`。
若用归一值做成员匹配，`星期.一` 永远查不到 `一`。

**修法**：`Member.name_text` 保存**源码原文**，声明端与访问端
统一按原文匹配（与反引号逃生舱共用 `parser._name_text()` 这一个入口）。

**为什么强调「唯一入口」**：这正是项目铁律「同一语义两处实现必然分叉」的
典型场景 —— 声明端按原文、访问端按归一值，两边各写一次，必然对不上。

### 节点 3：真实程序逼出的缺陷（本版核心）

**做法**：写一个三文件的多文件样例工程 `projects/库存管理/`
（领域模型 / 库存服务 / 主程序），定义类型 → 构造 → 流转 → 汇总 → 预警 →
CSV 导出，六步真实业务链路，**故意包含「库存不足」与「状态未完成」两个分支**。

**结果**：程序跑到第三步就崩了，暴露出 6 个**既有缺陷** —— 全都是
「写 demo 永远碰不到、写真实程序必然撞上」的那一类。逐个记录：

#### 缺陷 A：汉字名 + 拉丁后缀的源码原文被截断（**影响面最大**）

**症状**：`编码.编码Base64("你好")` 报「模块里没有『编码』这个成员」。
打印记号发现：`text="编码"`、`value="编码Base64"` —— **原文与值不一致**。

**根因**：`lexer._han_block` 在**吸收拉丁尾段之前**就取了 `raw_text`
（`self.raw[raw_start:self.pos]`）。对 `编码Base64` 而言，此时 `pos` 还停在
汉字 `编码` 之后，于是原文只有两字，而随后拼接的 `value` 是完整的。

**为什么影响面大**：凡「汉字名 + 拉丁后缀」的记号**全部**中招 ——
`编码Base64`、`解码Base64`、`导出CSV`… 全部查不到。而且报错文案指向
十万八千里外（先是「空不是函数」，后是「模块里没这个成员」），
**症状与根因的连线极长**，是最难定位的一类。

**修法**：把 `raw_text` 的取值移到**吸收完所有尾段之后**。

**回归测试**：新增分组「词法·汉字名加拉丁后缀」，同时断言
① 切分唯一；② `text == value`（原文完整）；③ 端到端能命中。

#### 缺陷 B：七个单字 A 类关键字前缀切坏高频词

**症状**：`系统.当前目录` 被切成 `系统.` + `当`(while) + `前目录`。

**根因**：`当` 是单字 A 类引导词，前缀匹配命中后即融合切分。
但凡以 `当` 开头的词（`当前`）都会中招。同类的还有
`令 当 若 让 设 试 请` 会切坏 `设备清单`、`设计图纸`、`设置参数`、
`请求登记`、`试验记录`、`请假`。

**修法**：新增 `A_SINGLE` 约束（与既有的 `C_SINGLE` 同口径）：
单字词**仅当剩余部分是「多字关键字」时**才融合切分。这样保住
`请假`（剩余是单字 `假`）、`让步`（剩余是单字 `步`，非关键字），
同时不破坏 `若成立` 这类融合写法。

#### 缺陷 C：内置函数收具名参数被完全静默丢弃

**症状**：`输出(甲 是 5)` **既不输出、也不报错**。

**根因**：`输出` 签名为可变参数，具名参数躲过了参数个数检查，
又在运行期被丢弃。

**为什么这是最严重的一类**：与项目铁律「静默失败比报错危险」**直接冲突**。
用户写错了代码，程序若无其事地继续跑 —— 这种错误可能在几千行之后才以
完全无关的症状爆发。

**修法**：新增 `_check_stray_kwargs()`，内置函数收到具名参数一律报 `D3007`。

#### 缺陷 D：用户函数具名参数不计数

**症状**：`问候(名字 是 "老李")` 误报「需要 2 个参数，给了 0 个」。

**根因**：语义层只数 `len(node.args)`，没算 keyword 参数。

**修法**：`_check_user_arity` 改签名，把 kwargs 计入总数，并校验未知具名参数；
运行期 `_call_shuyan` 同步改为 `bound = len(args) + len(kwargs)`。
（**语义层与运行期必须同序** —— 又一次落实这条铁律。）

#### 缺陷 E：成员名被归一化后查不到

**症状**：`文本.重复("a", 3)` 报「『空』不是函数，不能调用」。

**根因**：`重复` 是关键字（`loop`），`.重复` 的成员名被归一成 `loop`，
查不到成员 → 静默返回空 → 空被当函数调用 → 报错在十万八千里外。

**修法**：`_eval_Member` 与 `_expr_Member` 统一改用 `key = node.name_text or node.name`；
并对模块命名空间的缺失成员**明确报错**（此前是静默返回空）。

#### 缺陷 F：类型名当值使用拖到运行期才报

**症状**：`输出(点)` 在运行期才报错。

**修法**：新增 `_report_bare_type_use`，在**编译期**报 `D3005`
「类型名不能当作值使用」，并给出「是否想用 `类型名(...)` 构造」的建议。

### 节点 4：跨模块能力的三个连锁缺陷

多文件工程落地时，跨模块调用又暴露三个缺陷：
① 子解释器未传 `analyzer`，导致跨模块枚举成员表为空；
② 子解释器 `env` 未跟随 `global_env` 替换，语句写进旧环境、导出全空；
③ 语义层拒绝 `.sy` 文件引入，而运行期支持 —— **编译期与运行期口径不一致**。

②③ 促使将「候选路径与导出规则必须同口径」明确写进 SPEC §3.8.1。

### 节点 5：性能基准确立基线

**做了什么**：`benchmarks/run_bench.py`，七类用例，**编译期与运行期分开计时**，
取中位数（解释器受调度与 GC 干扰，均值易被离群值拉偏）。

**实测结果**（规模 10 万量级）：

| 用例 | 规模 | 编译期 | 运行期 |
|---|---|---|---|
| 循环·数值 | 100000 | 297 µs | 530 ms |
| 函数·调用 | 50000 | 340 µs | 351 ms |
| 递归·斐波那契 | 20 | 312 µs | 147 ms |
| 文本·拼接 | 20000 | 284 µs | 113 ms |
| 中文·字符计数 | 100000 | 406 µs | 1.17 s |
| 列表·追加遍历 | 100000 | 458 µs | 830 ms |
| 映射·哈希查找 | 50000 | 526 µs | 777 ms |

**三条结论**：
1. 10k → 100k 耗时约 10 倍，**线性增长，无平方级爆炸** ——
   文本拼接已验证不是 O(n²)（这是最需要警惕的一类性能陷阱）。
2. 中文处理约为纯算术的 2 倍，属**函数调用开销**（每次多调一层
   `长度`/`显示宽度`），在解释器的正常范围。
3. 编译期稳定在数百微秒，**远小于运行期** —— 印证了「只看总耗时会启动开销
   掩盖执行效率」这一判断。

### 节点 6：CLI 只处理第一个文件（**静默遗漏**）

**症状**：`sy 检查 examples/*.sy`（5 个文件）只输出 1 行 `✓`，
却让人以为全部通过。`sy 运行`、`sy 格式化` 同样只取 `args[0]`。

**为什么严重**：Makefile 的 `检查` 目标、CI 的静态检查步骤、
文档里的命令**全都**写成 `examples/*.sy` 形状 —— 也就是说，
自动化检查实际上**只验证了一个文件却报告通过**。
这比「检查没写」更危险：它制造了虚假的安全感。

**修法**：`检查` / `格式化` / `运行` 全部改为处理**全部文件参数**；
`运行` 顺序执行、任一失败即返回非零；`格式化` 非写入模式加文件分隔标注。

**教训**：「只看 `args[0]`」在 shell 世界里几乎总是错的 ——
glob 展开是常态，不是特例。

### 节点 7：格式化器破坏源码（**严重**）

**症状**：`sy 格式化` 把 `n <= 1` 改成 `n < = 1`，程序直接语法错误。
所有多字符运算符全部中招：`==` → `= =`、`+=` → `+ =`、`>=` → `> =`。

**为什么严重**：格式化器的契约是**只改外观、不改语义**。
把能跑的程序格式化坏，比不格式化严重得多 —— 而且它会在提交前批量
重写整个仓库的源码，一次事故污染全部文件（本次已实际写坏 `斐波那契.sy`）。

**根因**：`_is_complete_operator` **只向前检查、不向后检查**。
补空格的循环按 `("==", "!=", "<=", ...)` 顺序处理多字符运算符，
每轮都对**整个字符串**重新扫描。处理完 `==` 后字符串已是 `a == b`，
轮到单字符 `=` 轮次时：

- 首个 `=`：后面是 `=` → 正确跳过；
- **第二个 `=`**：后面是空格 → 被判为独立运算符 → 补空格 → `= =`。

**修法**：补上**向后检查** —— 本字符若紧跟 `=!<>+-*/%` 之一，
则它是多字符运算符的后半部分，不得独立处理。

**为什么既有测试没抓到**：格式化测试只用了 `>`（单字符），
**恰好绕开**了所有多字符运算符。这是「测试用例不覆盖真实写法 =
虚假的安全感」的典型案例 —— 于是新增分组
「格式化器·不得破坏多字符运算符」，覆盖 8 个多字符运算符 +
单字符补空格功能 + **幂等性**。

### 节点 8：语义层两处实现分叉（`callee.name` vs `name_text`）

**症状**：`sy 运行` 能跑通 `文本.重复`，`sy 检查` 却报
「模块『文本』里没有『loop』这个成员」。

**根因**：成员名的「取源码原文」逻辑在语义层有**两处**：
`_expr_Member`（成员访问）与 `_expr_CallTarget`（模块成员**调用**）。
前者已改用 `name_text`，后者仍用归一名 `callee.name` ——
`重复` 归一后是 `loop`，于是报错里带着 `loop` 这个内部名字。

**修法**：`_expr_CallTarget` 的模块成员分支同步改用
`key = callee.name_text or callee.name`。

**教训**：这正是项目铁律「**同一语义两处实现必然分叉**」的第 N 次应验。
本次是先修了访问路径、漏了调用路径，两条路径的差异只在
「后面有没有 `()`」—— 一个极易被忽略的分界。

### 节点 9：检查与运行的模块解析基准不一致

**症状**：`sy 运行 projects/库存管理/主程序.sy` 正常，
`sy 检查` 同一文件却报「找不到模块『领域模型』」。

**根因**：本机模块的解析基准是「主脚本所在目录」（SPEC §3.8.1）。
`sy 运行` 创建 `StdLib(base_dir=脚本目录)`，而
`sy 检查` 走 `lint_source()`，内部新建的 `StdLib()` 用的是默认
`base_dir=os.getcwd()` —— **编译期与运行期口径不一致**。

**修法**：`lint_source` 增加 `filename` 参数，据此设置 `base_dir`；
CLI 调用时传入路径。

**教训**：又一次「两处实现分叉」，只是这次分叉在**工具链**而非语言核心。

## 2026-10-20 · v0.2.2 端到端验证与诊断可行动化

### 动机：能力要靠跑通来证明，不靠功能列表

v0.2.1 之后浮现一个尖锐问题：**标准库 11 个模块全是本地能力，
没有一个网络模块 —— 那这门语言到底能不能写出有用的应用？**

这个问题不能靠「我们有闭包、有高阶函数」来回答。功能列表说明
「有什么零件」，不说明「组装起来能不能跑」。于是决定：**做一个真实
Web 应用，端到端跑通，用运行结果说话。** 若跑不通，那就是真实缺口，
照实写进边界声明，不修饰。

### 第一步：先探测，再决定做不做

先写最小验证脚本，逐项确认枢言在 Web 场景下到底缺什么：

| 探测项 | 结果 |
|---|---|
| 路由分发用纯函数 | ✅ 可行 —— 输入输出都是普通值 |
| 状态码作为业务返回值 | ✅ 可行 —— `{状态: 200, 内容: ...}` |
| HTML 渲染（字符串插值） | ✅ 可行 —— 现有语法足够 |
| 数据增删与计数 | ✅ 可行 —— 结构体列表 + 高阶函数 |
| **HTTP 收发** | ❌ **无标准库** —— 必须由宿主语言承担 |
| **中文 URL 路径** | ⚠️ **需服务端显式解码** —— 否则静默失效 |

探测的结论很明确：**业务层不缺，缺的是网络层**。于是把工作拆成
「枢言写业务」与「宿主写适配」两块，界线划在 HTTP 报文之外。

### 第二步：写应用，暴露真实问题

`projects/留言板/` 分三块：`应用.sy`（业务逻辑，123 行）、
`服务.py`（网络适配，127 行）、`README.md`（实测记录）。

过程中踩到三个真实的坑，都不是「语法不够」：

**坑 1 · 长表达式换行时运算符留在了行首**

`应用.sy` 里几个长表达式按常见习惯折行，把 `+` 写在了**下一行行首**，
结果整段报 `D3004`：`运算符「+」不能作用在「文本」上`。
错误码没错 —— 行首的 `+` 确实被当成了**一元运算符**，
而一元 `+` 只能作用于数字。

但定位**完全指错方向**：用户会以为字符串拼错了，实际是换行位置的问题。
枢言的续行规则（SPEC §2.7）要求运算符留在**上一行行尾**
（`+ - * / % ( [ , 且 或 是` 之一时自动续行）。

实测还确认了一个反直觉的细节 —— **括号能救场**：

| 写法 | 结果 |
|---|---|
| 行尾 `+`，无括号 | ✅ 运行，输出「你好世界」 |
| 行尾 `+`，有括号 | ✅ 运行 |
| **行首 `+`，有括号** | ✅ **运行**（未闭合括号内部忽略换行） |
| 行首 `+`，无括号 | ❌ D3004 |

所以「用圆括号括起来」是一条**真实可用**的替代写法，可以写进建议里。

**坑 2 · 中文 URL 路径静默失效**

请求 `/新增` 时，客户端与 `http.client` 都用 ascii 编码请求行，
直接抛 `UnicodeEncodeError`；即便客户端做了百分号编码，**服务端若不
`unquote`，中文路由也会匹配不上** —— 而且**不报错**，只是走进 404 分支。
这是「静默失败比报错危险」这条铁律在应用层的又一次现身。

**坑 3 · POST 看不到真实状态码**

`urllib` 默认自动跟随重定向，于是「提交后 302 跳回首页」在测试里
表现成 200，**把重定向验证变成了假通过**。改用不跟随重定向的
handler 才测到真实的 302。

### 修法：把错误提示改成「可直接照做的改法」

坑 1 的修法不是改语法（续行规则本身是对的），而是**改诊断**：
既然「行首一元运算符」绝大多数情况下不是用户本意，就直说该怎么办。

`semantic._expr_Unary` 新增建议：

> 如果是长表达式换行，请把运算符放在上一行行尾（枢言靠行尾运算符
> 自动续行）；也可以用圆括号把整个表达式括起来

原先只有「该运算符需要数字」—— 正确但没用。现在两句话：
**一条给规范写法，一条给绕过写法。**

### 第三步：为「建议」补测试

此前测试只断言**错误码**与**错误文案**，**建议（hints）游离在测试之外**。
这意味着：改动一动，错误码还在、文案还在，**建议悄悄丢了没人发现**。

新增 `expect_hint()`，把建议也纳入断言，并锁住四条相关行为：

- 行首 `+` 拼文本 ⇒ 报 D3004 且建议含「运算符放在上一行行尾」
- 上述同一例 ⇒ 建议含「圆括号」
- 括号内行首运算符 ⇒ **不报错**（SPEC §2.7 的边界，防回归）
- 行尾运算符续行 ⇒ 顺畅运行（正确写法必须畅通）

### 结果

端到端 **21/21 项通过**：真实 HTTP 请求，覆盖 200 / 302 / 404、
中文路由、数据增删、页面渲染。**没有为了让测试变绿而改实现**。

**一句话结论**：枢言缺的不是表达能力，是网络层的轮子。
业务代码与适配代码比例约 **1:1**，语言内核在真实场景中够用。

### 补记：把「通过 17 项」变成「可复现地通过 21 项」

最初这轮验证是**手工发请求、人眼读响应**，结论记成「17 项通过」。
问题很明显：**这个数字无法复现，也无法防止回归** ——
改一行代码，谁都不知道那 17 项还成不成立。

于是把它固化为 `projects/留言板/自测.py`：启动临时端口的真实服务，
逐项发请求、逐项断言、末行汇总。固化过程中出现两处**断言写错**，
恰好说明固化是有价值的：

| 原断言 | 实际行为 | 谁错了 |
|---|---|---|
| `GET /新增` 应返回 200 | 返回 **302** | **断言错** —— 302 恰是中文路径被正确解码并匹配到 `/新增` 分支的证据；若解码失败会落进 404 |
| 用 `GET /新增` 的响应体测「标题为留言板」 | 302 响应体为空 | **断言错** —— 页面标题该在 `GET /` 的响应体里测 |

两处都是**测试写错而非实现有问题**，但也因此暴露出一个此前没说清的真实简化：
**路由只按路径分发，不区分 HTTP 方法** —— 对表单端点发 GET 也会触发提交分支。
已写入 README 边界声明。固化后项数为 **21**（比手工统计更细），
数字与用例逐条对应，可随时复跑。

这正对应项目里的一条既有经验：**手写的临时结论不可信，能被反复执行的才算数。**

## 2026-10-19 · v0.2.1 高阶函数、错误恢复与表示统一

### 动机：先诊断根因，再动手

v0.2 发布后做了一次**成熟度自检**：把项目当作第三方交付物来审视，
找出「成熟项目不该有、而当前实现确实存在」的硬伤。

采用「先探测、后动手」的顺序 —— 不加没经过验证的功能，因为那属于
「用新增量掩盖旧问题」。自检结果如下：

| 自检项 | 实测结果 | 判断 |
|---|---|---|
| 错误恢复 | `定义 乙 == 2` 一行报 **4 条**错，且污染后续行 | ⛔ 硬伤 |
| 高阶函数 | 标准库**一个都没有**；写真实程序只能手写 `当` + `入列` | ⛔ 硬伤 |
| 输出表示 | 同一文本值在列表 `[甲, 乙]`、在映射 `{'甲': 1}` | ⛔ 不一致 |
| REPL / JSON / CSV | 均无 | 记入路线图 |

前三条立即开工（即本版三个主攻点）。

### 节点 1：错误恢复 —— 从「四倍报错」到「一行一错」

**症状**：一行 `定义 乙 == 2` 产生 4 条诊断，且后续**本来正确**的行也被报错。

**根因**：解析器遇错后**没有同步恢复点**。`_parse_call` 报「参数列表未闭合」
之后，调用方继续按「参数还在后面」的假设往下解析，于是同一根因被反复报告，
并一路吃掉了后续记号。

**修法**（三处配合，缺一不可）：

1. **行级恐慌恢复** `_sync_to_next_line(mark)`：进入语句时记下错误计数；
   语句结束时若计数增加，丢弃本行剩余记号、跳到下一行行首。
2. **`_guard_trailing_tokens` 重写**：原实现只拦截「像值」的记号，
   现在拦截**任何**残余记号 —— 但若本条语句**已报过错**则不再补刀
   （`_stmt_mark` 判断），避免二次报错。
3. **在调用与表达式处设卡**：参数位置若出现「语句起始关键字」，
   基本可判定是上一行漏了右括号 ⇒ 报一条「未闭合」并置
   `_suppress_followup`，抑制后续衍生报错。

**验证**（`test_error_recovery_one_per_line`，5 类场景）：
单行一错 · 不级联 · 两处独立错误报两条 · 未闭合括号只报一条 ·
正常程序零报错。

**设计取舍**：恢复点选「下一行行首」而非「下一个分号」。枢言以换行作
语句终止（SPEC §2.7），分号非必需，以分号为恢复点会漏掉大量情形。
**宁可保守** —— 放弃同行后续的发现，也不制造错误洪水。

### 节点 2：高阶函数 —— 回调宿主是绕不开的一环

**验证前置**：先确认枢言函数确为一等公民（`应用(平方, 5)` 输出 25，
匿名函数 `函数(x) 返回 x * 2 结束` 亦可用）。结论：可行。

**关键难点**：内置函数**拿不到解释器上下文**。枢言函数执行需要作用域链、
调用栈、返回信号（`ReturnSignal` 以异常传递），这些都在解释器手上。
内置函数自己无法执行枢言函数。

**修法**：**回调宿主注入**。解释器初始化时把自己的调用能力交给标准库
（`self.stdlib.callback = self._invoke_shuyan`）；内置函数经
`StdLib._invoke(fn, args, where)` 使用。

**过程中修掉的两个自身缺陷**：

- **`_invoke` 两条路径混用**：宿主函数（如 `绝对值`）也是 `callable`，
  曾与枢言函数走同一分支，会在 `_call_shuyan` 取 `fn.params` 处炸出宿主异常。
  → 分开：`ShuyanFunction` 走 callback，其余 `callable` 直接调用。
- **`error(...)` 写成 `return`**：`error()` **返回**异常对象，必须 `raise`。
  写成 `return` 会让「非函数参数」静默通过 —— 又一个静默失败。

**真值判断统一**：新代码误用了私有 `_truthy`（未定义），而文件里已有
`values.is_truthy`。**没有**另造别名（那正是「同一语义两处实现」）——
直接复用同一份，确保「标准库认为假」与「语言内 `如果` 认为假」永远一致。

### 节点 3：容器输出表示 —— 三份实现收敛为一份

**症状**（由高阶函数测试撞出）：

```shuyan
输出({"甲": 1})        # {'甲': 1}   ← 键带单引号
输出(["甲", "乙"])     # [甲, 乙]    ← 元素不带引号
```

同一文本值，在两种容器里长得不一样。

**根因**：容器渲染**写了三份**：
列表在 `display` 里手写一份、映射在 `ShuyanMap.__repr__` 写一份、
结构体在 `ShuyanStruct.__repr__` 再写一份。其中映射的键用了 Python 的
`{k!r}` —— 那是 **Python 的表示**，不是枢言的表示，单引号就是这么来的。

**修法**：收敛为**唯一容器渲染实现** `values._render(value, elem)`。
容器结构只写一份；`elem` 决定元素用哪种口径：

| 口径 | 元素文本 | 用途 |
|---|---|---|
| `_show_text`（不加引号） | `甲` | 用户输出路径（`display`｜`输出`｜`转文本`） |
| `_show_repr`（加引号） | `"甲"` | 调试表示（Python 层 `__repr__`） |

**连带修正**：`test_struct_text_nested` 原期望 `员工{姓名: "陈工"}`。
按新口径应不带引号 —— **这不是「改测试迎合实现」**，而是原期望本身
自相矛盾：`输出(甲.姓名)` 得 `陈工`，`输出(甲)` 却得 `姓名: "陈工"`，
同一个值取出来与整体打印不一致。SPEC §6.2.2 已把该口径写成硬性约束。

### 节点 4：把「没有的」也写进文档

本项目遵循一条原则：**不要让人误以为有那些东西**。据此在
README、SPEC、ROADMAP、CHANGELOG 四处如实声明实现边界：

| 维度 | 如实写法 |
|---|---|
| 执行方式 | **解释器**；**没有**字节码 VM、**没有** JIT（ROADMAP 阶段 P3） |
| 性能定位 | 「可用」非「最快」；不追求零开销抽象 |
| 类型系统 | **保守推断**，只在能推的地方推；**不是** HM 类型推导，**不是**借用检查 |
| 交互环境 | **无 REPL**（只能运行源码文件，ROADMAP 阶段 P2） |
| 调试 / 依赖 | **无调试器**（P2）· **无包管理器**（P4） |

SPEC 新增 §10.1「实现现状与已知限制」表与 §5.4.1「推断能力边界」
（明确列出**能推断的 6 类**与**推不出的 4 类**）。

**理由**：评估者按文档的承诺来判断工具。文档若暗示存在而实际不存在，
信任损失远大于功能缺失本身。**把「没有的」写清楚，与把「有的」写清楚同等重要。**
凡「运行能过、检查报错」的症状，第一反应就该是查两边的入口参数是否同口径。

### 节点 1：规范先行（SPEC.md 冻结）

**做了什么**：在写任何代码前，先冻结 `docs/SPEC.md`——词法、语法、类型、语义、

**为什么这样做**：中文编程语言的失败案例里，多数是从「先写个能跑的 demo」开始，

**规范内被修订的设计**（写规范过程中自己发现的矛盾）：

**动机**：此前所有示例都是单文件小程序，无法回答「多文件工程跑得起来吗」
「真实业务约束表达得出来吗」。于是用一个**真实财务系统**去压测语言本身。

### 节点 1：应收对账与账龄分析系统

`projects/应收对账/`，四文件分层工程：`领域模型` → `账龄服务` → `报表` → `主程序`。

业务口径按真实财务规范：金额**整数分**、信用管控、回款校验、
账龄四档分桶、中文列宽对齐。**全部用现有语法写出，未新增任何语言特性**。

结论与留言板一致并可互相印证：**业务表达能力充足，缺的是基础设施**
（网络 / HTTP 模块）。三个完整工程（库存 / 留言板 / 应收对账）覆盖了
CLI 批量处理、Web 服务、财务核算三类真实场景。

### 节点 2：最严重缺陷 —— 表达式语句静默丢弃

**现象**：报表渲染出来**整整一列数据是空的**，但零报错。

**根因**：长表达式换行时把 `+` 写在了**下一行行首**。枢言要求运算符写在
**上一行行尾**（SPEC §2.7）。行首的 `+` 于是成为**新语句**的开始（一元正号
表达式），整条拼接断裂，`+ 左对齐("单号", 14) + "  "` 被当作「算完就扔」的
语句**静默丢弃**。

**为什么之前没被拦住**：既有的负例测试覆盖过这个写法，但它期望的是语义期
的 `D3004`（「运算符不能作用在文本上」）。**当左操作数是数字时，`D3004`
根本不会报** —— 数字上的一元 `+` 完全合法。于是企业工程里这种形态
（`返回 右对齐(...) + "  "` 换行）连一个错都没有。

**修复**：新增解析期诊断 `D2012`。表达式语句的值算完就丢时**必须报错**，
提示指向根因（「运算符挪到上一行行尾」或「用圆括号括起来」）。

**判据的边界**（避免误报）：只对**纯计算**（算术 / 比较 / 逻辑 / 一元 /
字面量）报错；函数调用（有副作用）、变量 / 成员 / 索引单独成句仍放行 ——
后者常见于调试残留，不算「拼接断裂」。

**为什么是报错而非自动续行**：把行首运算符接回上一行会改变语言语义
（`-x` 独立成句将不再合法），也违背「规则确定」的承诺。规范已冻结，
故只把「沉默」改为「响亮」。

> 这条缺陷是「**静默丢弃比报错危险**」这一工程判断的最强证据：
> 结果错且无人察觉，比崩溃难查一个数量级。

### 节点 3：真因不可见 —— 参数遮蔽内置模块

**现象**：报「「文本」没有「填充」属性」，用户去文本模块翻 —— 那里明明有
`填充`，完全找不到问题。

**根因**：`请 左对齐(文本, 宽度)` 的参数 `文本` **遮蔽**了内置模块 `文本`，
函数体里的 `文本.填充(...)` 取到的是那个**字符串参数**。报错在**调用处**，
真因在**定义处**。

**修复**：两处补齐，都指向真因。

1. **定义处提醒（`W4001` 扩展）**：变量 / 参数 / 循环变量与内置模块名或
   核心函数名同名时，在**定义处**给警告 + 改名建议。
2. **运行期可行动提示**：成员访问失败且本地有同名名字挡住模块时，
   明确说明「是谁挡了路」。判据收紧到「该内置模块确实有这个名字的成员」，
   避免对普通字段错误乱猜。

### 节点 4：结构化提示被静默丢掉

补完运行期提示后，发现提示**写进了异常值却一个字都不显示**。

**根因**：`ShuyanThrow._describe`（Python 异常消息）与解释器
`_report_uncaught`（CLI 报错输出）**各写一份**「类型：信息」渲染。
新增「提示」字段时只改了其中一处。**又一次「同一语义两处实现必然分叉」**。

**修复**：收敛为唯一渲染入口 `errors.describe_error_value()`，两处共用。

### 节点 5：把「手工结论」变成「可复现探针」

新增两个探针，把发现过程固化下来：

- `tools/probe_stress.py`：8 大类边界共 66 用例，记录三种结果

## 2026-10-20 · 桌面工作台与括号吞行缺陷（v0.4.0）

### 节点 1：把工具链搬进图形界面，先做服务层收敛

**任务**：给编译器做一个桌面端。

**动手前的关键判断**：不能直接写界面。命令行（`cli.py`）与图形界面
需要**完全相同**的编译行为；若各写一份，必然分叉 —— 这是本项目反复踩到的
工程铁律。**先抽服务层**：新增 `shuyan/workbench.py` 作为六种操作
（运行 / 检查 / 格式化 / 词法 / 语法树 / 自测）的**唯一实现**，
返回结构化的 `Outcome`（而非裸字符串，因为界面要按诊断类别着色，
需要**诊断对象**而不是预先渲染好的文本）。

然后把 `cli.py` 的 `_compile` / `_dump_ast` / `_too_deep_diag` /
`_render_with_files` / `_run_one` / `cmd_lex` / `cmd_ast` 全部改为调服务层。
重构后命令行行为**逐字不变**（21 文件检查、六示例、ERP 自证两式全部照旧）。

**界面实现的两个要点**：

1. **高亮复用词法器，不另写扫描器**。注释、字符串、全角归一化、
   汉字块切分这些规则只该有一份。但有个陷阱：**列号口径不同** ——
   词法记号的 `Span.col` 是**显示列**（汉字算 2 列），而编辑器索引按**字符**。
   故高亮坐标不用 `Span.col`，改为**在行内按记号原文定位**，拿到真实字符下标。
   混用两种口径，中文行的着色会整段偏移。
   注释还有个依据：`Lexer` 在括号开着时不发换行记号，故「记号之间的空档」
   就是注释与空白 —— 用空档倒推注释区间，规则只有一份。
2. **运行与自测放后台线程**。ERP 套件约两分钟，放界面线程里窗口会卡住。
   其余四种是毫秒级，直接做更简单。

**tkinter 不是所有发行版都自带**：开发用的托管 Python 就没有。
故写 `shuyan/launcher.py` 探测可用解释器 —— 探测必须**真的建一次窗口**，
只测 `import tkinter` 会得到假通过（Tcl 库缺失时 import 成功、`Tk()` 才失败）。

### 节点 2：括号未闭合时吞掉下一整行（**静默丢弃**）

做界面时要写「故意含错」的样本验证诊断展示，随手写了：

```
定义 甲 = 1
输出(甲 + )        ← 第 2 行
定义 乙 = 2        ← 第 3 行：完全正确
```

**实测发现**：报错位置指向**第 3 行行首** —— 一条完全正确的语句被扣上
「参数列表未闭合」的帽子。更严重的是第 3 行**整行被丢弃**，
AST 里没有 `乙`。若第 3 行是 `输出(乙)`（`乙` 未定义），那条语义错也一并消失，
`检查` 反而显示「没有发现问题」。**这是 v0.3.1 没修完的部分**：语法错仍会
吞掉后续行的语义错，只是这次吞的不是「诊断」而是**整行源码**。

**定位方式：插桩，不推测**。逐层打印 `_parse_call` / `_parse_statement` /
`_sync_to_next_line` 的进入退出游标，看到：

```
_parse_call 退出 [11]KEYWORD:'let'@3   ← 已跨到第 3 行
_parse_statement 退出 [16]EOF@4        ← 一路推进到文件尾
诊断: D2003@2:11, D2002@3:1            ← 第二条指着第 3 行
```

**两个根因，都不在 v0.3.1 的修改范围内**：

① **`_skip_newlines()` 跨过了语句边界**。依据在词法层：`Lexer.tokenize` 里

```python
if self.paren_depth > 0 or self._emit_prev_category():
    continue            # 抑制 NEWLINE
```

即**只要括号还开着，词法器根本不发出换行记号**。反读就是：
「括号组内出现 NEWLINE」= 括号早已配对完毕、**组已经断了** ——
原先却把它当成「组还长着，要跨过去」，于是越过了一整行。

② **恢复点算错一行**。语句收尾的 `_skip_terminators` 会把行尾换行吃掉，
游标已落在**下一行行首**；此时找「行尾」找到的是**再下一行**，
中间那整行就被吞了。

**修法**：

1. 新增 `Parser._group_unclosed()`，**调用参数 / 列表 / 映射 / 分组括号
   四处同一口径**。判据必须**两条**，缺一不可：
   - 当前是 `NEWLINE`（组已闭合、语句在此收尾）；
   - **或**当前是语句起始关键字（`_at_stmt_start`）。
     这一条不可省 —— 括号没闭合时换行被词法层抑制掉了，
     解析层看不到 NEWLINE，只能靠「这句关键字不可能出现在值的位置」判定。
     只有前一条会漏判 `(1 + 2` 后跟 `定义 丁 = 4` 的情形。
2. 恢复点**预计算**：进入语句时就算好「本语句所在逻辑行的下一行行首」，
   恢复时**只前进、不回退**。

### 节点 3：第一版修法把编译器改成了死循环（**自己踩的坑**）

第一版让 `_sync_to_next_line` 在游标已越过起始行时**退回去重扫**。

结果：`sy 测试` 卡死不动。用 `faulthandler` 抓栈看到
`_parse_statements → _parse_block → _parse_if` 的深层递归；
再插桩数循环次数，200 层 `如果` 的用例**游标在 576~600 之间往返**、
错误数涨到 **82 万**。

**机理**：深层嵌套退栈时，**每一层**都会调用一次恢复。层 A 把游标退回本层
起始行 → 扫描到行尾 → 前进一行；层 B 接着又把游标退回**它自己**的起始行
（在 A 之前）→ 再前进……每层回退一行、再前进一行，**互相覆盖**，成环。

**教训（已写入方法注释）**：**错误恢复只能单调前进**，
任何形式的回退在多层退栈时都会成环。

### 节点 4：症状收敛 —— 同一处不补刀

改完后 `输出(甲 + )` 报出**三条**：缺操作数 D2003、参数列表未闭合 D2002、
括号不匹配 D2002 —— 但用户只错了一处。

判据原先只看 `_suppress_followup`（由表达式层在「运算符右边撞上语句边界」时置位），
漏掉了「**同一条语句里前一段已经报过错**」的情形。
新增 `Parser._no_error_yet()` 统一两条判据：

```python
return (self._error_count == self._stmt_mark
        and not self._suppress_followup)
```

四个括号组收尾处统一改用它。改后 `输出(甲 + )` 只报一条，
报告落在**未闭合的那个 `(`** 上（真因处），第 3 行完好无损。

### 残留在本地实跑里的验证

改完解析器后，不只跑测试，还逐项确认**没有把合法特性一起禁掉** ——
`examples/结构体与枚举.sy` 与 `examples/高阶函数.sy` 里都有**多行参数列表**
（`线段(起点 是 点(...),
终点 是 点(...))`），它们必须仍然合法。
实测两个文件 `检查` 均为「没有发现问题」。

**如果只跑测试就收工，这条会被漏掉** —— 既有测试里没有多行参数列表的用例。

## 2026-10-20 · ERP 工程与 10 万行级压力测试（v0.3 主线）

**动机**：此前的三个工程最多 4 个文件、几百行。它们能证明「语法够用」，
却回答不了规模问题 —— **上百个模块、十万行代码跑得起来吗？多深嵌套、
多长的表达式、多大的集合会让它崩？** 于是在 ERP 工程之后，专门做了一套
**可复现的 10 万行工程**与一套**极端场景探针**，用规模去逼出缺陷。

结论先行：**逼出 6 处真缺陷，其中 2 处属「宿主崩溃」级**——这类缺陷
小规模测试永远碰不到，只有上万行、或有极端输入时才会暴露。

### 节点 1：ERP 工程（六模块分层）

`projects/ERP/`，六文件：`主数据`（类型与主数据）→ `库存服务`
（移动加权平均 + 盘盈亏）→ `采购服务` → `销售服务` → `财务服务`
（复式记账）→ `企业`（**状态持有 + 事务编排**）。

关键架构决策：**服务层无状态纯函数**，状态集中在一处。理由是枢言的
赋值是**引用语义**（`定义 乙 = 甲` 是引用，切片与映射合并只是浅拷贝），
服务层若随手改入参，调用方持有的对象会被悄悄改掉，跨模块排查极难。
分层后依赖单向、无循环引入、无共享引用陷阱。

**事务编排**用「两阶段提交」绕过「没有回滚」的限制：
预演阶段只调纯函数、**绝不改状态**（连凭证号都不发，用空号占位去校验
借贷平衡），全部通过后才提交。这样「中途失败不回滚」就不再伤害到账。

**自证式设计**：主程序末尾让工程**自己核对两件事**，不靠人肉验算 ——
① 试算平衡（全账借方合计 == 贷方合计）；② 存货核对（库存台账金额 ==
总账「库存商品」科目余额）。后者是 ERP 最容易出错的地方：成本结转或
记账漏一笔，两套账就对不上。把核对做成**程序输出**，跑一遍即知成不成。

**业务层自身修掉的一个缺陷：状态机少一态。**
初版单据状态机只有 `草稿 / 已审核 / 已完成`，缺 `已执行`。后果有两层：
① 一个订单**部分收货后恰好收齐**，状态直接跳「已完成」；而**已收一部分
但未收齐**的订单状态仍是「已审核」，与「一行未动」的订单**无法区分**。
② 更糟的是报错文案：继续收货时报「订单未审核，不能收货」，
而真因是「已收齐」—— **报错点与真因点不一致**，人会往错方向查。

修法：启用枚举里**早已定义却从未使用**的 `已执行`（这本身就是信号：
定义了不用，多半是状态机没想全）；收货/发货置 `已执行`，收齐才置
`已完成`；失败文案按**实际状态**分三种（未审核 / 已收齐 / 已作废）。
这与项目反复出现的教训同源：**报错点 ≠ 真因点时，必须在真因处说清**。

### 节点 2：可复现的 10 万行工程生成器

`tools/gen_big_project.py` —— 按**确定性规则**生成多文件工程
（同一命令两次运行逐字节一致）。这解决了「压测不可复现」的老问题：
手工攒十万行代码不现实，也无法每次重来。

规模（实测）：`--modules 200 --records 3000 --funcs 24 --types 60`
⇒ **202 个文件、105700 行、3.3 MB**。

### 节点 3：极端场景探针

`tools/probe_extreme.py` —— 44 个用例，专测**规模与极端形态**：
超长标识符（10 万字）、超长字符串（100 万字）、超大集合（50 万元素）、
深层嵌套、超深调用链、编码边界、符号量级。判定基准只有一条：
**宿主异常算失败**（`CRASH`），无论报错文案多好。

### 缺陷统计（本轮，全部可复现）

| # | 缺陷 | 分类 | 症状 |
|---|---|---|---|
| 1 | 数字后的 `_` 切断标识符 | **真缺陷** | `服务001_校验` 被切成两枚记号，报「`校验` 两侧没有运算符」 |
| 2 | 嵌套太深 → 宿主 `RecursionError` | **宿主崩溃** | 1000 层括号 / 500 层列表 / 1000 层 `如果`，用户看到 Python 堆栈 |
| 3 | 按名引入类型 → 宿主 `AttributeError` | **宿主崩溃** | `引入 { 类型 } 从 "模块"` 直接崩 Python |
| 4 | 整模块引入后裸用类型名假通过 | **假通过** | `sy 检查` 报「没问题」，运行必崩，且位置是「第 0 行 0 列」 |
| 5 | 枚举成员表靠回查顶层分析器 | **真缺陷** | `模块.枚举.成员` 取到空成员表，报「没有成员 X。可用成员：」（空） |
| 6 | 模块路径解析两处各写一份 | **隐患** | 语义层与运行期候选路径可能分叉（已收敛为唯一入口） |

#### 缺陷 1：数字后的下划线切断标识符

**症状**：`账簿006_借方合计` 被切成 `账簿006_` + `借方合计`，
报出「`贷方合计` 两侧没有运算符」—— 与真因相距十万八千里。

**根因**：`lexer` 的混合标识符判定只认两种情况 ——「汉字块紧跟 `_`」
与「下划线在字块内」。而下划线出现在**数字之后**时，两种都不满足，
于是汉字段走了另一条路径重新切分。

**为什么危害大**：SPEC §2.5 明确允许 `订单_ID`、`user_编号` 这类混合
标识符；真实工程里 `服务001_校验`、`账簿006_借方合计` 是极自然的命名。
生成器一跑就撞上，说明这不是边角情形。

**修法**：判据收敛为「**只要 `_` 出现过，后续的字母/数字/汉字都并进
同一枚标识符**」，与 `_latin_word` 同口径。且**必须循环**——
`A1_账_余额` 有多段，早期只吸收一轮仍会切断第二段。

#### 缺陷 2：嵌套太深撞爆宿主栈（**宿主崩溃**）

**症状**：1000 层括号、500 层列表、1000 层 `如果` 全部抛
`RecursionError` —— **一段 Python 堆栈**，不是枢言诊断。

**根因**：递归下降解析器每层嵌套消耗数层 Python 调用栈，
而默认递归上限是 1000。实测每层消耗：
括号 ≈ 3.1 帧、列表 ≈ 4.2 帧、`如果` ≈ 4.2 帧 —— 故边界约 320 / 240 / 240 层。

**修法（两道并存）**：
① 解析器在**唯一入口** `_parse_expression` 与 `_parse_block` 加深度守卫，
   超限报 `D2013` 并给「拆成中间变量 / 函数」的建议；
② 编译边界（`cli` / `linter`）兜底捕获漏网的 `RecursionError`，转成同一条诊断。

**为什么两道都要**：递归深度预算是**结构相关**的 —— 不同语法形态每层
消耗帧数不同，单靠一个常数无法覆盖全（第一版取 300，结果 500 层列表
仍在守卫触发前就崩了）。守卫负责「给出好建议」，兜底负责「绝不崩宿主」。

**阈值 180 的来历**：取最紧形态（240）× 75%，留 25% 余量。这个数字
是**实测出来的**，不是估的（`tools/probe_extreme.py` 可复现）。

#### 缺陷 3 & 4：跨模块类型的两个分叉

**缺陷 4 是「假通过」**：`引入 "模块"`（整模块引入）后**裸用**模块里的
类型名，`sy 检查` 报「没有发现问题」，但运行期必然报「没有定义」——
而且错误位置显示为**「第 0 行，第 0 列」**（运行期的类型查找拿不到源码位置），
用户完全无从下手。

**根因**：语义层把被引入模块的类型「并入」了本文件（不分引入形式），
运行期却按 SPEC §3.8.1 只绑命名空间 —— **语义层宽松、运行期严格**，
于是假通过。

**修法**：语义层不再无条件并入，改为按引入形式区分（与 SPEC 完全一致）；
裸用时在**编译期**报 `D3005`，并给出两种可照做的改写
（`模块.类型` 或 `引入 { 类型 } 从 "模块"`）。

**缺陷 3 是「宿主崩溃」**：`引入 { 类型名 } 从 "模块"` 让 Python 抛
`AttributeError: 'NoneType' object has no attribute 'type'` ——
因为类型不放在作用域符号表里，导出值为 `None`，代码却直接读 `.type`。
用户看到的是 Python 堆栈。修法是遇到 `None` 走「按名引入类型」分支。

**缺陷 5**：`ShuyanType` 不自带成员表，运行期靠回查 `self.analyzer`。
但那是**顶层**分析器，不认识被引入模块的类型 ⇒ 取到空成员表。
修法是让类型**自描述**（`members` / `fields` 挂在类型对象上），
随命名空间一起飞行 —— 凡是类型自己能回答的问题，就不该去问环境。

#### 缺陷 6：模块路径解析收敛为唯一入口

语义层与运行期各自写了一份候选路径生成代码。这是项目铁律
「同一语义两处实现必然分叉」的**隐患点**（还没出事，但迟早出事）。
修法是抽 `StdLib.resolve_module_file()` 作为唯一入口，两处都调它。

### 节点 4：压测发现的**规范歧义**（写进 SPEC，不改实现）

`一百二十` 既能按 §2.5 理解为标识符，又能按 §2.6 理解为数字字面量。
实现选择**数词优先**，故 `定义 一百二十 = 5` 报 `D2002`。

**为什么不改实现**：把 `一百二十` 判为数字是日常使用频率远高的一面，
且数词识别**确定性**（不依赖上下文猜测）。反过来让标识符优先，
`输出(一百二十)` 就成了未定义变量 —— 那更常错。
已记入 SPEC「已知歧义」，并指明反引号逃生舱可用。

## 2026-10-20 · 语法错吞掉同文件语义错（v0.3.1）

**来源**：本地实跑编译器演示时，随手写了个「故意含错」的文件，
结果只报语法错、**不报语义错** —— 一查才发现这不是偶发，而是稳定行为。

**症状**：一个文件里同时有语法错与语义错时，`sy 检查` **只报语法错**。

```
定义 甲 = 1
甲 是 "文本"        # ← 语义错：文本不能赋给整数（D3004）
输出(甲 加 2)       # ← 语法错：`加` 两侧没有运算符（D2001）
```

实测只报 D2001，**D3004 一条不报**。用户必须先改语法、重跑，才看到类型错 ——
被迫来回两趟，且完全不知道为什么第一次没报。

**为什么危害不小**：这属于「**漏报**」，与静默失败同族 ——
用户以为自己改完了、程序干净了，其实还有错没露出来。

**根因**：`lint_source` 调 `Parser.parse()`，而 `parse()` **一见到诊断就
`raise ParseError`**：

```python
if self.diagnostics:
    raise ParseError(self.diagnostics)   # ← 整棵（已恢复的）AST 就此丢掉
```

`lint_source` 捕获异常后 `return None, exc.diagnostics` ——
`program` 是 `None`，**语义分析根本不会运行**。

讽刺之处：解析器**早已实现行级错误恢复**（`_sync_to_next_line`），
遇错后继续往下解析、能产出一棵**部分合法的 AST** —— 恢复的努力，
被末尾这一行 `raise` 自己抵消了。

**与规范冲突**：SPEC §8.2 第 5 条白纸黑字写着「一次编译**报告全部错误**
（不遇错即停）」。实现没做到。⇒ 修实现，不改规范。

**修法**：

1. 新增 `Parser.parse_recovering()` —— **有诊断也返回 `(部分 AST, 语法诊断)`**，
   不抛异常。`parse()` 改为它的薄封装（有诊断则抛），供运行路径使用 ——
   运行一个语法错的程序本就不该继续。
2. `lint_source` 改用 `parse_recovering()`：拿到部分 AST 后
   **继续跑语义分析**，把语法诊断与语义诊断**按（行，列）稳定排序合并**。
   - 排序是必需的：合并后若不排序，会出现「第 7 行的错显示在第 3 行的错前面」，
     用户按行往下改时对不上。
   - 词法阶段的 `LexError` 仍直接返回 —— 没有记号流，语法/语义都无从谈起。

**验证**（`test_parse_and_semantic_errors_reported_together`，四类断言）：

| 断言 | 防的是 |
|---|---|
| 语义错 + 语法错共存 ⇒ 两类都要有 | 修复本身 |
| 诊断按行号升序 | 合并后乱序 |
| 名字**均已定义**时不得冒出语义诊断 | 合并导致**误报** |
| 正常程序零诊断 | 合并路径误伤正常程序 |

> 第三条最初写错了：用 `输出(甲 +)` 做「纯语法错」样本，结果冒出 `D3005` ——
> 但 `甲` 确实**没定义**，那条诊断是**真**的，不是误报。样本必须先 `定义 甲`，
> 才能隔离出「合并是否凭空多出诊断」这一个变量。
> ⇒ 测试样本要**只动一个变量**，否则测出来的东西不是你以为的那个。

**教训**：这条缺陷的发现方式值得记 —— 它不在任何既有测试里，
是**人在本地实跑、随手写错误代码**撞出来的。
⇒ **「故意写错」也是一种测试**：既有测试只验证「该报的报了」，
不验证「除了该报的还报了什么」。
