# 枢言（Shuyan）· 设计白皮书

> 版本 0.1 · 2026-10-19 · 阿枢
> 本文说明**为什么这样设计**。语言的形式定义在 `SPEC.md`，实施进度在 `ROADMAP.md`。

---

## 一、枢言要解决的问题

中文程序员面对的真实困境，不是「关键字不认识」，而是这四条：

| 编号 | 困境 | 现有中文语言的处理 | 枢言的取舍 |
|---|---|---|---|
| P1 | **中文没有词间空格**，关键字与标识符必然粘连 | 多数要求强制空格，或用空格分词 | 三级字块单趟裁决算法，规则可预测、无回溯 |
| P2 | **中文输入法频繁切换**，全角/半角混用 | 报「非法字符」 | 词法层归一化 + 明确区分「意图明确」与「意图不明」 |
| P3 | **报错看不懂**，是弃用的首要原因 | 沿用英文报错或简译 | 报错即教学：行号 + 列号（按显示宽度）+ 修复建议 + 拼写候选 |
| P4 | **中文语言常被当作玩具**，缺工程属性 | 生态薄弱，不敢用于生产 | 规范先行、诊断码体系、测试体系、格式化器与 Lint 齐备 |

## 二、核心设计决策与理由

### 决策一：双前端口语 / 书面语 → 同一棵 AST

**做什么**：同一门语言提供两种表面语法。

```shuyan
# 书面语
如果 年龄 >= 18 则
    输出("成年")
结束

# 口语（白话）
若 年龄 不小于 18，那么
    说一声"成年"
完
```

**为什么可行**：两种表面形式在**词法层**就被归一到同一批关键字语义名
（`if` / `let` / `is` / `for`），解析器只按语义名分派。**白话不是另一门语言，
只是同一语法树的另一种输入皮肤。**

**为什么不做成两门语言**：两套语法 = 两套语义 = 两倍的 bug 面积，
且两边的库不能互调。归一化到同一 AST，白话才能复用全部工具链。

**代价（诚实说明）**：
- 白话需要「句读逗号」这类自然语言特例兜底（`若 甲 大于 3，那么` 里的 `，` 无语义）；
- 无括号调用（`说 名字`）只能**白名单**开放，不能通用——否则与「两条相邻表达式语句」无法区分。

### 决策二：三级字块裁决算法

**问题**：`定义年龄=20` 要切成 `定义` + `年龄`；而 `数据中台` 必须整体保留。

**算法**（SPEC §2.4）：对每个连续汉字段，按固定顺序尝试三通道——

1. **A 类前缀**（引导词在块首）：`定义年龄` → `定义` + `年龄`
2. **C 类后缀**（联结词在块尾）：`年龄是` → `年龄` + `是`
3. **C 类中缀**（联结词在块中，**仅限长度 ≥ 2 的多字词**）：`名单中每个名字` → `名单` + `中` + `每个名字`
4. 都不命中 → 整体标识符

**关键约束——单字词不参与中缀切分**：

| 若允许中缀 | 后果 |
|---|---|
| `数据中台` | 裂成 `数据` + `中` + `台` ❌ |
| `期中成绩` | 裂成 `期` + `中` + `成绩` ❌ |
| `其中原因` | 裂成 `其` + `中` + `原因` ❌ |

这三例在中文里都是**极常见的词**。故单字联结词（是/为/叫/从/到/中/里）
**只允许作整块命中或块尾切分**，绝不允许出现在块中参与切分。

**为什么不用分词库**：通用中文分词器面向自然语言，会把 `定义年龄` 切成
`定义`+`年龄`（对）但也会把 `数据中台` 切成 `数据`+`中台`（错）。编程语言需要的是
**确定性与可预测**，不是统计最优。故自研规则算法，不引入统计模型。

### 决策三：保留名整体保护

**问题**：`类型名` 是内置函数，但 `类型` 是 A 类关键字。前缀匹配会把它切成 `类型` + `名`。

**方案**：维护一份 `names.py` 保留名清单（内置函数 / 模块 / 类型名），
在切分前**先做整体命中检查**。命中则整块作标识符，不做任何关键字切分。

**代价**：用户不能把这些名字用作变量名。这是可接受的——内置名本就是语言的一部分。

### 决策四：报错即教学（诊断系统）

一条诊断必须包含五要素：**行号、显示列号、诊断码、源码摘录 + 下划线、修复建议**。

```
第 5 行，第 9 列：语义错误（D3004）
  不能把「文本」赋值给「整数」变量 年龄。

    5 |     年龄 是 "二十岁"
      |            ^^^^^^^^ 此处得到 文本

  → 建议：改用 整("二十岁")，或把 年龄 声明为 文本。
```

**显示宽度是硬性要求**：汉字占 2 列，下划线必须按显示列对齐。
不做这件事，中文源码的报错下划线必然错位——这是中文语言工具链的入门门槛。

**拼写候选**（D3005）：未定义标识符时按编辑距离给出「你是不是想写 X」。

### 决策五：假值表显式化

条件判定采用「真值语义」而非「仅布尔可作条件」：

- **假值**：`假`、`空`、`0`、`0.0`、`""`、`[]`、`{}`
- **真值**：其余一切

**理由**：中文程序员的直觉接近自然语言判断——「有名字就……」，不该强制写 `长度(名字) > 0`。

**代价**：必须明确列出假值表，否则出现「为什么空列表是假」的争论。规范已完整列举。

**配套**：`且`/`或` 返回**操作数本身**（而非强制转布尔），使 `名字 或 "匿名"` 这类写法成立。

### 决策六：被否决的设计（记录在案）

| 曾计划 | 否决理由 |
|---|---|
| `2 的 10 次方` 作幂运算符 | 中文「的」字出现频率极高（`我的名字`、`系统的状态`），定为运算符需回溯解析，与「词法单趟」核心承诺冲突。改用 `次方(底, 指数)` 或 `^` |
| 函数重载 | 中文参数名同形率高（`甲`、`值`、`数据`），重载判定易产生意外歧义。以 `D3003` **明确报错**，引导改用可选参数——诚实排除，不假装支持 |
| 静态检查只报第一个错 | 修一个跑一次，体验极差。改为**聚合报告全部错误**（上限 50 条后汇总） |
| 缩进敏感语法 | 中文缩进宽度在不同编辑器下不一致，视觉判断不可靠。块用 `结束` 或 `{ }` 显式封闭 |

## 三、与既有中文编程语言的关系声明

**枢言的设计独立完成**。参考的仅是**公开的、属于常识层面的语言设计问题**
（中文分词歧义、全角符号、UTF-8 处理），**不复制**任何既有中文编程语言的：
源码、关键字表、语法文件、编译器实现、运行时。

具体而言：

| 维度 | 说明 |
|---|---|
| 关键字表 | 本项目自行拟定，以「汉语语义自然度 + 与算法关键字无碰撞」为准 |
| 词法算法 | 自研三级字块裁决（前缀/后缀/中缀三通道） |
| 语法算法 | Pratt 表达式解析 + 递归下降（通用编译原理技术，非特定实现） |
| 运行时 | 自研树遍历解释器 + 值模型 + 异常模型 |
| 标准库 | 全部自研；模块划分参考主流语言的**通用分类**（文本/列表/数学/时间/文件），非特定语言接口 |
| 生态兼容 | **无**——不设任何既有中文语言的兼容层 |

唯一借鉴的是**通用编译原理**（词法/语法/语义分析、Pratt 解析、作用域链、
树遍历求值），这些属于公共领域的计算机科学基础。

## 四、v0.1 的能力边界（诚实清单）

**已实现**：中文关键字与标识符 · 三级切分裁决 · 双端口语/书面语 · 中文数词字面量 ·
全角归一化 · 插值字符串 · 完整表达式与语句 · 闭包与默认参数 · 异常模型 ·
语义分析与类型检查 · 中文诊断系统 · 标准库（11 模块） · 格式化器 · Lint · CLI · 自测体系

**未实现（路线图内）**：结构体/枚举 · 泛型 · 模块化导入多文件工程 · 调试器 ·
包管理器 · 字节码 VM · JIT · LLVM 后端 · IDE 插件 · FFI · 并发 · 独立发布安装包

**已知限制**：
1. 单字联结词（是/为/中/从/到/里/叫）在**无空格且夹在汉字之间**时无法切分——
   这是中文无空格的固有代价，规范选择显式化而非启发式猜测。
2. 无括号调用仅 `说` / `输出` / `打印` 可用。
3. `符号`（字形簇）级字符处理未做，按 Unicode 码点处理（emoji 组合符会被视为多个字符）。
4. 正则表达式沿用 Python `re` 语法，未做中文优先改造。

---

## 五、一句话总结

> 枢言不是为了证明「中文能编程」——那早已不是问题。
> 它要解决的问题是：**让中文编程具备工程属性**——
> 确定的切分规则、教学式的报错、可测试的语义、可维护的工具链。
