# 枢言（Shuyan）

**中文原生编程语言 · 从零自研的完整编译器工具链**

> 不是「把英文关键字翻译成中文」的玩具，而是从语言规范到编译器、
> 从标准库到格式化器的**完整工程实现**。纯 Python 标准库，零第三方依赖。

---

## 三十秒了解

```shuyan
# 书面语
定义 订单数量 = 100
定义 单价 = 12.5

如果 订单数量 > 50 则
    输出("批量订单，总额：" + 转文本(订单数量 * 单价))
结束

# 白话文（同一语法树的另一种写法）
设 名字 是 "陈工"
说一声 `你好，{名字}！`
```

```bash
$ sy 运行 示例.sy
批量订单，总额：1250.0
你好，陈工！
```

## 核心特性

| 特性 | 说明 |
|---|---|
| **中文原生词法** | 中文关键字与标识符直接可用，`定义年龄=20` 与 `定义 年龄 = 20` 等价 |
| **双端口语/书面语** | 白话文与形式中文**产出同一棵 AST**，不是两门语言 |
| **中文数词字面量** | `三`、`一百二十`、`十五`、`十亿`、`3万` 都是合法字面量 |
| **全角符号归一化** | `（）`、`＝`、`；` 自动识别；意图不明的标点（`《》`）明确报错 |
| **系统性消歧** | 三级字块单趟裁决算法，规则确定、无回溯、可预测 |
| **报错即教学** | 行号 + 显示列号 + 诊断码 + 源码下划线 + 修复建议 + 拼写候选 |
| **UTF-8 中文完整支持** | 长度按字符算、对齐按显示宽度算（汉字 = 2 列） |
| **完整工具链** | 词法器 · 语法器 · 语义器 · 解释器 · 格式化器 · Lint · CLI · 自测 |
| **高阶函数** | 函数是一等公民；内置 `筛选` `映射列表` `归约` `排序依据` `分组依据` 等 10 个 |
| **一行一错** | 一条语句出错只报一条，不级联、不污染后续行 |
| **零依赖** | 纯 Python 标准库，不引入任何第三方库或语法文件 |

## 快速开始

**环境要求**：Python 3.10 以上（开发环境为 3.13.12）。无需安装任何依赖。

```bash
# 运行程序
python sy.py 运行 examples/你好世界.sy

# 静态检查（不执行）
python sy.py 检查 examples/斐波那契.sy

# 格式化源码
python sy.py 格式化 examples/中文切分演示.sy --写入

# 查看中文词法切分（学习切分规则的好工具）
python sy.py 词法 examples/中文切分演示.sy

# 查看语法树
python sy.py 语法树 examples/你好世界.sy

# 运行自测（59 项，应全部通过）
python sy.py 测试
```

> **注意**：当前**没有 REPL**。枢言只通过 `sy 运行 <文件>` 执行源码文件，
> 没有交互式输入环境 —— 直接运行 `python sy.py` 不带子命令会打印用法说明。
> REPL 在路线图（`docs/ROADMAP.md` 阶段 P2）中。

### 安装为命令（可选）

pip install -e .

## 设计要点速览

### 三级字块裁决（中文切分的核心）

中文没有词间空格，切分是根本难题：

```shuyan
定义年龄=20          →  定义 + 年龄 + = + 20      （A 类前缀）
年龄不小于18         →  年龄 + >= + 18            （C 类后缀）
数据中台 是 1        →  数据中台 + 是 + 1         （单字词**不**中缀切分）
遍历名单中的每个名字  →  遍历 + 名单 + 中 + 每个 + 名字
```

**关键约束**：单字联结词（是/为/中/从/到/里/叫）**不允许在中缀位置切分**——
否则 `数据中台`、`期中成绩`、`其中原因` 这些极常见的词都会被切坏。
规范选择**规则确定**，而非统计猜测。

### 报错即教学

```
第 5 行，第 9 列：语义错误（D3004）
  不能把「文本」赋值给「整数」变量「年龄」。

    5 |     年龄 是 "二十岁"
      |            ^^^^^^^^
  · 此处得到的类型是「文本」
  → 建议：改用 整("二十岁")，或把 年龄 声明为 文本。
```

列号按**显示宽度**计算（汉字占 2 列），下划线才能对齐。

### 被否决的设计（记录在案）

- ❌ `2 的 10 次方` 作幂运算符 → 中文「的」字太常用，会造成大量歧义。改用 `次方(2, 10)`
- ❌ 函数重载 → 中文参数名同形率高，易产生意外歧义。以 `D3003` 明确报错，诚实排除
- ⛔ 缩进敏感语法 → 中文缩进宽度在同一编辑器下判断不可靠，改用 `结束` 显式封闭

## 与既有中文编程语言的关系

**本项目完全独立自研**，不复制任何既有中文编程语言的源码、关键字表、
语法文件、编译器实现或运行时。

- 关键字表：自行拟定（以汉语语义自然度 + 无碰撞为准）
- 词法算法：自研三级字块裁决（前缀/后缀/中缀三通道）
- 语法算法：Pratt + 递归下降（通用编译原理技术）
- 运行时与标准库：全部自研
- 兼容层：**无**

唯一借鉴的是**公共领域的通用编译原理**（词法/语法/语义分析、Pratt 解析、
作用域链、树遍历求值）。

### 实现边界（**如实声明，避免错误预期**）

| 维度 | 现状 |
|---|---|
| 执行方式 | **解释器**（直接遍历 AST 求值），**没有字节码 VM，也没有 JIT** |
| 性能定位 | 「可用」，**不追求**零开销抽象；已有基准套件提供对照基线 |
| 类型系统 | **保守推断**，只在能推的地方推；推不出即 `任意`，**不是** HM 类型推导，**也不是** Rust 式借用检查 |
| 交互环境 | **无 REPL**，只能运行源码文件 |
| 调试能力 | **无调试器**，靠诊断信息定位 |
| 应用范围 | 业务逻辑层（路由、状态码、数据增删、模板渲染）**已端到端验证可用**；**网络层缺失**，需由宿主语言承担 |

> 上述五项均在 `docs/ROADMAP.md` 中规划。写在这里是为了让评估者一眼看清
> 「现在有什么、没有什么」—— 把边界说清楚，与把功能说清楚同等重要。

### 端到端验证：能写完整应用吗？

标准库 11 个模块全是**本地能力**（文本 / 数学 / 集合 / 时间 / 文件 /
编码 / 随机 / 系统 / 路径 / 格式 / 类型），**没有网络模块**。那么枢言能不能
写一个完整可用的应用？已用一个真实 Web 应用回答：`projects/留言板/`。

| 层 | 由谁实现 | 说明 |
|---|---|---|
| 路由分发 | **枢言** | `处理请求(路径, 表单)` 纯函数，输入输出皆为枢言值 |
| 状态码语义 | **枢言** | `200 / 302 / 404` 作为业务返回值显式给出 |
| 数据增删与计数 | **枢言** | 结构体列表 + 高阶函数，全用现有语法 |
| HTML 渲染 | **枢言** | 字符串插值直接生成页面 |
| HTTP 收发与线程 | Python | 127 行适配层，**一行业务逻辑都不放** |

**结论**：业务代码与适配代码比例约 **1:1**，端到端 **21/21 项实测通过**
（真实 HTTP 请求，含 302 跳转、404 兜底、**中文 URL 路径**）。枢言缺的不是
「表达能力」，而是「网络层的轮子」—— 这与 JavaScript 之于 Node、Python
之于 WSGI 的早期处境相同：语言内核够用，标准库待补。详见
[`projects/留言板/README.md`](projects/留言板/README.md)。

### 端到端验证：能扛住真实业务吗？

Web 应用证明了「能跑起来」，但业务约束（金额精度、信用管控、中文报表）
尚未被压力测试。为此新增一个**企业级财务工程**：`projects/应收对账/`。

四文件分层（`领域模型` → `账龄服务` → `报表` → `主程序`，依赖单向），
覆盖真实财务口径：金额**整数分**、信用额度拦截、回款校验、账龄四档分桶、
中文列宽对齐 —— **全部用现有语法写出，未新增任何语言特性**。

| 业务需求 | 实现方式 | 结果 |
|---|---|---|
| 金额精确到分 | 全程整数分，无浮点 | ✔ 零误差 |
| 信用管控 | 新单 + 现有应收 > 额度即拦截 | ✔ 拦截生效 |
| 回款校验 | 须 > 0 且 ≤ 未收余额 | ✔ 超额/零额均拦截 |
| 账龄分桶 | 按逾期天数分四档 | ✔ 边界正确 |
| 中文表格 | 按**显示宽度**对齐（汉字 2 列） | ✔ 列对齐整齐 |

**结论**：四个完整工程（库存管理 / 留言板 / 应收对账 / ERP）覆盖 CLI 批量处理、
Web 服务、财务核算、企业套件四类真实场景，共同印证同一判断 ——
**业务表达能力充足，缺的是基础设施**。详见
[`projects/应收对账/README.md`](projects/应收对账/README.md)。

> 这个工程还是**发现真缺陷最多**的一个：它的用法足够「真实」，因而暴露出了
> 「行首运算符断行使整列数据静默消失」这类在小示例里根本撞不到的缺陷。
> 这也是「用真实项目压测语言」而非「用玩具示例自证」的价值所在。

### 端到端验证：企业级套件能分层放下吗？

单点业务（一张报表）能写，不代表**多模块互相依赖的套件**能写。为此再上一个
规模更大、耦合更深的工程：`projects/ERP/`，六个模块分层单向依赖 ——
`主数据`（类型中枢 + 编号/金额工具）→ `库存服务`（移动加权平均 + 盘盈亏）→
`采购服务` → `销售服务` → `财务服务`（复式记账）→ `企业`（状态持有 + 事务编排）。

| 业务约束 | 实现方式 | 结果 |
|---|---|---|
| 复式记账 | 有借必有贷、借贷必相等、凭证不可改只能红冲 | ✔ 三铁律校验 |
| 成本核算 | 移动加权平均；出库**先乘后除再取整**减少截断 | ✔ 利润表与总账相符 |
| 事务一致性 | **两阶段提交**：预演只调纯函数不改状态，全过才提交 | ✔ 中途失败不伤账 |
| 状态管理 | 服务层无状态纯函数，状态集中一处，**整体替换**避免引用共享 | ✔ 无跨模块串改 |

**关键发现**：枢言的赋值是**引用语义**（`定义 乙 = 甲` 是引用，切片与映射合并只是
浅拷贝），服务层若随手改入参，调用方持有的对象会被悄悄改掉。分层 + 整体替换
是绕开这一陷阱的可行解 —— 这也是一条**通用工程口径**，已写入文档。

### 规模压测：十万行能跑吗？

前面的工程最多几百行，回答不了规模问题。为此做了一套**可复现的规模测试**：

| 工具 | 作用 | 实测结果 |
|---|---|---|
| `tools/gen_big_project.py` | **确定性**生成多文件大工程（同命令两次运行逐字节一致） | 202 文件 / 105700 行 / 3.3 MB |
| `tools/probe_extreme.py` | 44 项极端形态探针（超长标识符/字符串、超大集合、深嵌套、编码边界） | 宿主崩溃 0 · 超时 0 · 静默错误 0 |

10 万行工程：**全量检查 202 个文件零问题**（约 80 s），**主程序完整跑通退出码 0**（约 120 s）。

> 规模测试**逼出 6 处真缺陷**，其中 **2 处是「宿主崩溃」级**（用户看到的是 Python
> 堆栈，不是枢言诊断）：数字后的下划线切断标识符、嵌套太深撞爆宿主栈、
> 整模块引入后裸用类型名「假通过」…… 这些在小示例里永远碰不到。
> 根因与修法见 [`docs/DEVLOG.md`](docs/DEVLOG.md)。
